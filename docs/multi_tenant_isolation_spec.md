# 多用户隔离需求规格（Multi-Tenant Isolation Spec）

> 适用对象：前端开发 + 前端 AI 辅助工具
> 背景：竞赛系统 XH-202630「领域知识个性化生成与多智能体协同决策系统」
> 目标：让系统真正支持**每位学员独立使用**，而非所有学员数据塌缩为单一"超级学员"

---

## 1. 问题陈述（Problem Statement）

当前系统的全部学情数据——知识盲区热力图、资源难度匹配曲线、学习路径规划图、学情画像、贡献记忆——均以 `session_id` 为隔离键落库。后端**已具备会话级多租户隔离能力**。但系统**缺失用户身份层（User Identity Layer）**：无 `user_id`、无登录/注册、无"学员 ↔ 会话"持久化映射。

这带来两类实现风险：

- **风险 A（数据混叠）**：若前端为所有学员复用同一个 `session_id`，则不同学员的学习轨迹、热力图、画像会叠加成**单一"超级学员"**——既违背个性化，也触碰答题（5）"用户画像数据脱敏、合规使用"红线。
- **风险 B（连续性丢失）**：若前端在每次页面刷新时新建随机 `session_id`，则学员学习进度永远从零开始，热力图无法体现成长轨迹，丧失"学习诊断"意义。

你观察到的现象——"问得越多热力图越满，看起来只服务了一个人"——本质就是**单个学员 session 内部的领域掌握度累积**（正确行为），但前提是每个学员必须拥有**独立且持久**的 session，否则就会退化成风险 A。

---

## 2. 现状审计（Current State Audit）

| 维度 | 现状 | 代码证据 |
|---|---|---|
| 数据隔离粒度 | `session_id` 级 | `backend/api/routes/report.py` 全部 `WHERE session_id = ?` |
| 用户身份 | 不存在 `user_id` / 账号 | 全仓 grep 无 `user_id` / `login` / `register` |
| 会话归属 | 完全由调用方（前端）传入 | `ask.py` 直接采用请求体 `AskRequest.session_id` 作为隔离键（全链路 `request.session_id`），并由 `compliance.ensure_session()` 自动为传入的 session 建表记录——前端无需自建 session 表 |
| 参考页实现 | 每次刷新随机 `demo-session-<Date.now()>` | `frontend_reference.html:232` |
| 离线加速开关 | `demo_cache_enabled` 默认 `False` | `backend/config.py:100` |

**审计结论**：后端数据层已可服务任意多学员并发隔离；缺口仅在于**前端驱动 + 身份层**。后端无需重构。

---

## 3. 功能需求（Functional Requirements）

- **FR-1** 每位学员必须拥有**稳定且唯一的 `session_id`**，在同一浏览器 / 账号下跨刷新、跨对话持续复用（禁止每次刷新重建）。
- **FR-2** 前端须维护"学员身份 ↔ session_id"映射。推荐方案：以学员标识（学号 / 手机号 / 本地账号）为 key 存 `localStorage`；或登录后由服务端下发 session。
- **FR-3** 切换学员 / 多账号场景下，调用后端接口（`/api/ask`、`/api/tasks`、`/api/ws/{task_id}`、`/api/report/{session_id}`、`/api/quiz_submit`）必须携带**对应学员的 session_id**，严禁全局共用一个。
- **FR-4** 所有学情视图（热力图 / 画像 / 学习路径 / 难度曲线）必须按 `session_id` 渲染——后端已按 session 过滤，前端正确传参即可，无需额外接口。
- **FR-5** `demo_cache_enabled` 在多用户 / 生产环境**必须保持 `False`**。该开关开启后 `/api/ask` 会按问题文本返回相同缓存答案给任何人，将直接摧毁个性化。

---

## 4. 范围澄清（Scope Clarification）

- **演示视频**：不要求多账号。视频展示单学员从画像 → 调度 → 资源的完整旅程，正是赛题"差异化学情画像输入"要求；多用户反而不聚焦，**无需在视频呈现**。
- **真实部署 / 提交**：须满足 FR-1 ~ FR-5，确保"每位学生都能独立使用"。建议在《作品介绍》/ 部署说明补"多用户就绪性"章节，说明后端 session 隔离能力与前端需完成的工作。

---

## 5. 验收标准（Acceptance Criteria）

- **AC-1** 两名学员各自学习同一领域，其热力图独立累积、互不干扰。
- **AC-2** 学员刷新页面后，学习进度与热力图连续（不重置为空白）。
- **AC-3** `demo_cache = False` 时，不同学员输入相同问题，产出按其各自画像差异化。

---

## 6. 给前端实现的落地提示

1. 不要依赖 `frontend_reference.html` 的随机 session 写法（`demo-session-` + 时间戳），那仅用于单页 demo，无连续性。
2. 若暂不做登录系统，最低成本方案：`localStorage` 按学员标识持久化 session_id，切换学员时读对应值。
3. 后端接口契约不变，无需新增端点；所有多用户能力来自"前端正确管理与传递 session_id"。
