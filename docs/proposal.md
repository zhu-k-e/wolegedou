# 第一部分：项目概述

## 1.1 选题背景

大模型在职业教育领域落地的核心矛盾：单一模型架构下，"个性化适配"与"专业质量把控"难以调和。尤其在 AI 大模型应用开发这一新兴赛道，知识更迭极快，学习者背景差异巨大——从零基础文科到算法工程师——对培训系统的个性化能力和专业准确性提出了极高要求。

本赛题要求构建**多智能体协同决策系统**。我们的方案以四模块架构为骨架——**学情诊断Agent、领域知识生成Agent池、审核团队+裁判团、贡献记忆闭环**——深度整合 DyLAN、Debate、MAR、MetaGPT 四篇顶会论文的核心发现，构建完整的"分析→生成→校验→决策→交付"主闭环 + "验证→调整→追问"延伸闭环，实现**交付后动态迭代**（降维解释/进阶挑战/启发式追问），打破静态资源单向输入局限。

### 1.2.1 "辩论与交叉验证"机制对齐说明

> **赛题原文**：引入"辩论与交叉验证"机制。本方案通过两层辩论 + 三重交叉验证满足：

**第一层：多立场独立审核（审核团队）**

审核团队3人从不同立场对同一答案进行独立审查，分歧通过评分差异自然体现，无需显式回合制辩论：

| 角色 | 审查立场 | 审查方式 |
|------|---------|---------|
| Verifier | "事实核查方" | 逐条核查知识点是否正确 |
| Skeptic | "反方挑战者" | 主动寻找逻辑漏洞和反例 |
| Evaluator | "教学适配方" | 从学生视角判断回答是否适合当前水平 |

三方独立评分，汇总计算加权总分——不同立场的审查已覆盖所有可能质疑角度。

**第二层：裁判团分歧解决 + 候选Agent辩论**

裁判团3人独立审查聚焦输出，互不可见（防锚定效应）。2:1分歧时触发**两层辩论**：

| 辩论层 | 参与者 | 机制 |
|--------|-------|------|
| 裁判团分歧解决 | 裁判团3人 | 少数方举证→多数方回应→僵持时裁判长裁决 |
| 候选Agent辩论 | 落选候选+获胜候选 | 落选方质疑+获胜方辩护，证据合并提交裁判团 |

候选Agent辩论是**Debate论文的真正落地**——让真正懂领域的内容生产者参与交叉验证，而非仅靠裁判（外行审查内行）判断。

**与自由辩论的区别**：本方案在裁判团阶段采用结构化辩论（立场固定、输出Schema固定的对抗博弈），而非自由辩论。原因是AI培训场景需要确定性输出，自由辩论不可控（可能跑题、冗长）。审核团队的多立场独立评分与裁判团的结构化辩论+候选辩论共同满足赛题"辩论与交叉验证"要求。

# 第二部分：模块一——学情诊断Agent

> 对齐赛题术语：**"分析"阶段**，对应赛题所述"学情诊断Agent"。

## 2.0 模块输入输出规格

**输入**：
- `question: str` — 学生当前问题（必填）
- `session_id: str` — 会话ID（用于增量更新时查历史画像）
- `history: list[dict] | None` — 历史对话（同一session，首次为 None）

**输出**：
- `StudentProfile`（JSON，见2.2.2节输出Schema）
  ```json
  {
    "knowledge_level": "入门/中级/进阶",
    "domain_hint": ["LLM基础", "Prompt工程"],
    "intent_type": "generation/navigation/clarification",
    ...
  }
  ```

**处理逻辑摘要**：
1. 构造 Prompt（2.2.5节模板）
2. 调用 LLM 生成/更新学情画像
3. 根据 `intent_type` 路由（2.3节三步调度框架）
4. 若 `intent_type=generation` → 输出候选Agent列表（见2.4节）
5. 若 `intent_type=navigation` → 输出学习路线图（Markdown）
6. 若 `intent_type=clarification` → 输出澄清选项（list[str]）

> 本模块**只负责学情诊断和调度**，不评分、不生成内容。后续模块见第三部分（Agent池）和第四部分（审核+裁判）。

## 2.1 功能定义

学情诊断Agent由两部分组成：
- **学情画像生成器**：根据学生输入问题（及可选的历史对话），生成或增量更新结构化学情画像。
- **调度员（Matcher）**：根据学情画像+问题复杂度，从Agent池遴选候选Agent。**调度员仅属于模块一**，不参与审核团队的评选或裁判团的裁决。

> **边界说明**：调度员在审核阶段无advisory角色。审核团队三人意见冲突时，以Verifier（事实准确性）权重最高解决，不由调度员裁量。

## 2.2 学情画像生成

### 2.2.1 输入

```
输入1: 学生当前问题（必填）
输入2: 历史对话记录（可选，首次咨询为空）
```

### 2.2.2 输出Schema（严格JSON格式）

```json
{
  "knowledge_level": "入门 / 中级 / 进阶",
  "background": "文科 / 理科_无编程 / 有Python基础 / 有ML基础",
  "current_goal": "快速上手应用 / 深入理解原理 / 项目落地 / 算法研究",
  "question_type": "概念理解 / 操作步骤 / 调试排错 / 架构设计 / 全链路规划",
  "domain_hint": ["LangChain", "Prompt工程", "RAG", "HuggingFace", "模型微调", "向量数据库", "Agent框架", "项目部署"],
  "complexity_estimate": "单领域 / 跨领域 / 全链路",
  "intent_type": "generation / navigation / clarification",
  "domain_confidence": {
    "LangChain": "high / low",
    "RAG": "high / low"
  },
  "test_results": [
    {"topic": "Prompt工程", "score": 0.72, "date": "2026-07-01"},
    {"topic": "RAG检索", "score": 0.45, "date": "2026-07-01"}
  ]
}
```

> **字段说明**：
> - `intent_type`：意图裁决结果，决定走哪条处理路径（见2.3节三步调度框架）。
> - `domain_confidence`：对每个domain_hint的置信度评估，用于调度员判断领域关联的可靠性。
> - `test_results`：**可选拓展字段**（对齐赛题要求"整合学习者先验知识画像（如学历背景、理论测试结果）"）。学生可上传理论测试成绩作为画像输入源，`score`为该知识点正确率（0-1），用于补充学情诊断的精确度；未上传时该字段为空数组`[]`，不影响正常流程。

### 2.2.3 推断规则

| 学情字段 | 推断依据（从问题中提取） |
|---------|----------------------|
| `knowledge_level` | "LangChain是什么？"→入门；"Memory和Buffer区别"→中级；"LoRA微调梯度累积设置"→进阶 |
| `background` | 提到"我是文科生"→文科；代码片段含`import torch`→有Python基础；提到"我训练过BERT"→有ML基础 |
| `current_goal` | "我想快速做一个聊天机器人"→快速上手；"我想深入理解Attention机制"→深入理解原理 |
| `question_type` | "什么是X"→概念理解；"怎么安装X"→操作步骤；"报错XX"→调试排错 |
| `domain_hint` | 问题中出现的领域关键词，由LLM从限定枚举值中选择，可多选 |
| `complexity_estimate` | 见2.3节详细规则 |
| `intent_type` | 见2.3.1意图裁决规则 |
| `domain_confidence` | 见2.3.2领域解析规则 |

### 2.2.4 增量更新机制（含画像缓存优化）

> 对齐赛题要求：连续对话场景下学情画像需随学生提问动态演进。

**画像缓存复用（代码实现优先策略）**：

为节省LLM调用（每次~3秒），同一session已有画像时直接复用，仅在首次提问时调用LLM生成。

```python
# 代码实现逻辑（profile_agent.py）：
latest = profile_repo.get_latest_profile(session_id)
if latest:
    cached_profile = self._profile_from_dict(latest)
    if cached_profile:
        return cached_profile  # 复用已有画像，跳过LLM调用
```

**真正的增量更新（后续版本）**：

当前v7.0采用**画像缓存复用**优先策略（已实现），真实的多轮历史综合评估（检索近3次历史→LLM重新输出）计划在V2.0中实现。

缓存复用与增量更新的取舍：

| 策略 | 响应时间 | LLM调用成本 | 画像准确度 | 实现状态 |
|------|---------|-------------|-------------|---------|
| 缓存复用（当前） | ~2s（仅DB读取） | 0次/轮 | 较高（首轮LLM生成质量高） | ✅ 已实现 |
| 增量更新（V2.0） | ~5s（含LLM调用） | 1次/轮 | 更高（综合历史判断） | 🔜 计划中 |

> **设计理由**：v7.0使用缓存复用作为性能优化（方案书§8.4.2优化2），首轮LLM画像已覆盖知识水平、意图、领域等核心字段。对于竞赛演示场景，同一session短对话内学生知识水平不突变，缓存复用不会显著降低精度。

```
触发条件（V2.0增量更新）：
  1. **必须触发**：同一session内，学生第2次及以后提问
  2. **不触发**：
     - 学生明确说"重新开始"或"换个话题"
     - session间隔超过30分钟（视为新对话）

更新策略（EMA评估）：
  1. 检索该session最近3次问答（不够3次则取全部）
  2. 新问题+近3次历史 → 画像生成器综合评估，输出新画像
  3. 比较差异字段：
     - knowledge_level：根据近3次问题综合判断，允许升级也允许降级
       （例：前2次问高级问题后问基础问题→合理降级，说明学生在复习基础）
     - domain_hint新增领域 → 合并（保留旧领域+新增领域，不删除）
     - background不变 → 保持（背景信息不随对话改变）
  4. 写入student_profiles表，**版本号+1，并记录变更字段**

变更追踪示例：
```json
{
  "session_id": "sess_001",
  "version": 3,
  "changed_fields": ["knowledge_level", "domain_hint"],
  "change_reason": "学生提问涉及LangChain高级用法"
}
```

### 2.2.5 Prompt模板

```

历史对话：{history}

请从以下枚举值中选择，不要自创值：
- knowledge_level: ["入门", "中级", "进阶"]
- background: ["文科", "理科_无编程", "有Python基础", "有ML基础"]
- current_goal: ["快速上手应用", "深入理解原理", "项目落地", "算法研究"]
- question_type: ["概念理解", "操作步骤", "调试排错", "架构设计", "全链路规划"]
- domain_hint: 可从["LLM基础", "Prompt工程", "LangChain", "RAG", "HuggingFace", "模型微调", "向量数据库", "Agent框架", "项目部署"]中选择多个，无匹配则留空数组[]
- complexity_estimate: ["单领域", "跨领域", "全链路"]
- intent_type: ["generation", "navigation", "clarification"]
  · generation: 问题含具体技术内容/动词，需要生成内容
  · navigation: 学生要方向推荐/路线图（关键词含"推荐/方向/路线/资源"），且无具体技术目标
  · clarification: domain_hint为空且非导航请求，学生想学但说不清学什么
- domain_confidence: 对每个domain_hint评估置信度，值为{"领域名": "high/low"}
  · high: 问题中直接提及该领域或明确相关操作
  · low: 仅间接关联，不确定是否真正需要
  · 不使用medium，简化调度逻辑

只输出JSON，不要输出其他内容。
```

## 2.3 三步调度框架

> 学情画像生成后，调度员需决定：走哪条处理路径？调几个Agent？调哪些Agent？本节给出覆盖1~10个Agent、处理模棱两可问题的统一方案。

### 2.3.1 Step 1：意图裁决

画像生成器输出的`intent_type`字段决定问题的处理路径：

| intent_type | 判断条件 | 处理路径 |
|-------------|---------|---------|
| **generation**（生成型） | 问题含具体技术内容/动词，domain_hint非空 | → Step 2正常调度Agent池 |
| **navigation**（导航型） | question_type=概念理解 + 无具体技术动词 + 关键词含"推荐/方向/路线/资源" | → 输出学习路线图，追问学生选择具体阶段 |

### 2.3.2 Step 2：领域解析

generation型请求进入此步。调度员根据`domain_hint`、`domain_confidence`和`complexity_estimate`确定段数和每段领域。

**复杂度评估规则**：

| `domain_hint`数量 | `question_type` | 复杂度判定 | 拆段方式 |
|-------------------|----------------|-------------|---------|
| 1个 | 任意 | **单领域** | 1段，该领域对应2个候选Agent |
| 2-3个 | 非"全链路规划" | **跨领域** | 2-3段，每个领域1段 |
| 4个以上 | 非"全链路规划" | **跨领域** | 每个领域1段，每段2个候选（固定） |
| 任意 | "全链路规划" | **全链路** | 按完整流程步骤拆段，3-5段 |

**核心原则：每段固定2个候选Agent**。即便某领域只有一个"最匹配"的Agent，调度员也必须从次匹配Agent中选一个补上，确保审核团队有输出可比较。

**领域置信度处理**：

调度员检查`domain_confidence`，决定是否纳入每个领域：

| domain_confidence情况 | 处理方式 |
|----------------------|---------|
| 全部high | 全部纳入，正常拆段调度 |
| 有low | 纳入但标注为"弱关联"，审核团队重点关注 |
| 全部low | 问题太泛，退回clarification路径 |

**模棱两可问题示例**：

```
问题："大模型应用开发怎么做"

画像：
  domain_hint = ["LLM基础", "Prompt工程", "LangChain", "RAG"]
  domain_confidence = {"LLM基础": "low", "Prompt工程": "low",
                       "LangChain": "low", "RAG": "low"}

→ 4个全是low → 退回clarification
→ 输出："你想从哪个方向入手？①入门基础 ②应用开发 ③模型微调"
```

```
问题："RAG和向量数据库是什么关系，怎么用"

画像：
  domain_hint = ["RAG", "向量数据库"]
  domain_confidence = {"RAG": "high", "向量数据库": "high"}
  complexity_estimate = "跨领域"

→ 全high → 拆2段，段1选RAG候选，段2选向量数据库候选
```

> **优先级说明**：当画像中的 `complexity_estimate`（LLM生成）与Step 2根据 `domain_hint` 数量/`question_type`/`domain_confidence` 的判断结果不一致时，**以Step 2的判断为准**。原因：Step 2额外参考了 `domain_confidence`，能识别"看似多领域但实际只有部分高置信度"的情况，判断更可靠。

### 2.3.3 Step 3：候选遴选

确定段数后，每段按统一规则从Agent池遴选候选Agent。

**遴选公式**：

```
综合权重 = α × 功能匹配度 + (1-α) × importance_score(function_tag)
```

- `功能匹配度`：根据Agent的primary_function / secondary_functions / domain_tags与当前段domain_hint的匹配程度计算（见2.4.1）
- `importance_score(function_tag)`：该Agent在此功能标签下的历史表现分（见5.4节）
- `α`：冷启动0.9→数据积累后0.3（见2.4.2）

**统一调用模式**：

> **背景**：每次LLM API调用实际耗时2-5秒（取决于模型、网络及输出长度），直接并发受限于API速率上限（如OpenAI GPT-4o：10,000 TPM）。系统统一采用**2候选 + 3人审核 + 3人裁判**的完整流程，审核与裁判各需3次独立LLM调用（并行发出，每次以不同角色Prompt执行，三次调用由同一个Agent实例发起）。每段总调用9次。

**1~7个领域的完整调用估算表**：

| 领域数 | 段数 | 候选调用 | 审核调用 | 聚焦调用 | 裁判调用 | 跨段审查 | 总调用 | 实际响应时间 |
|--------|------|---------|---------|---------|---------|---------|--------|------------|
| 1 | 1 | 2 | 3 | 1 | 3 | 0 | **9次** | **~20s** |
| 2 | 2 | 4 | 6 | 2 | 6 | 1 | **19次** | **~27s** |
| 3 | 3 | 6 | 9 | 3 | 9 | 1 | **28次** | **~33s** |
| 4 | 4 | 8 | 12 | 4 | 12 | 1 | **37次** | **~38s** |
| 5 | 5 | 10 | 15 | 5 | 15 | 1 | **46次** | **~43s** |
| 6-7 | 6-7 | 12-14 | 18-21 | 6-7 | 18-21 | 1 | **55-64次** | **~48s** |
| 8-10 | 触发分阶段 | — | — | — | — | — | **先回答前3领域** | **~33s/批次** |

> **双低RAG增强额外调用**：当某段2个候选的self_confidence都<0.5时（约15-20%场景），触发知识库RAG增强。每个候选重新生成一次（K=3知识库检索+LLM调用），每段额外+2次候选调用。加权后平均每段额外≈0.3-0.4次，已在上述估算的容差范围内。

> **超过7领域时的分阶段策略**：先回答最核心的3-5个领域（按domain_confidence=high优先），在答案末尾提示"剩余领域将在下一轮补充"。避免单次响应超过45秒。
>
> **全链路降级策略**：审核团队3人全部调用失败 → 跳过审核，所有候选直接进入聚焦输出（前端显示黄色警告"未经多角度审核"）。裁判团3人全部调用失败 → 跳过裁判，直接输出聚焦结果 + 标注"未经裁判团审查"。部分失败（2人成功1人失败）→ 取2人均值+标注置信度降低。若学情画像生成也失败 → 使用上次缓存的画像（session内持久化）。
>
> **候选辩论额外调用**：当裁判团出现2:1分歧时（约30%场景），触发候选Agent辩论（落选候选质疑+获胜候选辩护），额外+1-2次调用。加权后单领域平均额外调用≈0.3-0.6次，已含在上述估算的容差范围内。
>
> **注意**：上表仅统计核心管线的LLM调用（候选+审核+聚焦+裁判），不含学情画像生成（+1次）和资源生成阶段（讲义+1次，实操指南和测试题为条件触发+1~2次）。单领域场景的**完整调用量约11~13次**（含学情+资源生成）。

## 2.4 调度员选人机制

### 2.4.1 标签匹配度计算

每个Agent在SQLite中存储两条标签：

**功能标签**（人工预置，冷启动用）：
```json
{
  "agent_id": "agent_003",
  "primary_function": "LangChain组件开发",
  "secondary_functions": ["RAG架构", "Memory模块"],
  "domain_tags": ["LangChain", "RAG", "Prompt工程"]
}
```

**表现标签**（系统自动积累，跑起来后生效）：
```json
{
  "agent_id": "agent_003",
  "LangChain组件开发": {"accuracy": 0.89, "count": 23, "rework_rate": 0.22},
  "RAG架构": {"accuracy": 0.85, "count": 15, "rework_rate": 0.33},
  "Prompt工程": {"accuracy": 0.45, "count": 5, "rework_rate": 0.60}
}
```

> **注意**：表现标签按function_tag粒度存储，每个Agent在每个功能标签下有独立的accuracy/count/rework_rate。importance_score也是per-function-tag计算（详见5.4节）。

**匹配度计算**：
```
功能匹配度 = 
  若 primary_function 匹配 domain_hint → 1.0
  若 secondary_functions 匹配 → 0.7
  若 domain_tags 匹配 → 0.5
  否则 → 0
```

### 2.4.2 综合遴选权重（α动态切换）

```
综合权重 = α × 功能匹配度 + (1-α) × importance_score(function_tag)

其中：
  importance_score(function_tag) = 0.5×accuracy + 0.3×(1-rework_rate) + 0.2×count_normalized
      其中 count_normalized = min(count / 100, 1.0)
  （详见第五部分贡献记忆闭环）
```

**α初始值及衰减规则**：

| 积累数据量 | α值 | 说明 |
|------------|------|------|
| 0-100条 | 0.9 | 冷启动，主要依赖人工功能标签 |
| 100-200条 | 0.8 | 表现标签开始有统计意义 |
| 200-500条 | 0.5 | 表现标签与功能标签各占一半 |
| 500条以上 | 0.3 | 主要依赖跑出来的表现数据 |
| 1000条以上 | 0.2 | 表现标签完全主导 |

> **工程权衡声明**：α为**全局参数**（存储在SQLite的`system_config`表中），而非per-function-tag独立值。原因：per-function-tag的α需要每个function_tag积累足够数据才能准确计算衰减（约200条/function_tag），冷启动阶段全局α更稳定。当系统积累到1000条以上数据时，可升级为per-function-tag独立α。

α值存储在SQLite的`system_config`表中，每次贡献记忆更新后自动调整（按总数据量而非per-tag数据量）。

### 2.4.3 动态淘汰

```
触发条件：某个Agent在某一功能标签下，
          连续3次 importance_score(function_tag) < 0.5

阈值依据：
  - "连续3次"：基于DyLAN论文实验，3次连续低分可排除偶然因素
  - "importance_score < 0.5"：基于MAR论文，0.5是"及格线"
  - 阈值可配置：存储在`system_config`表，可根据实际数据调整

动作：
  1. 将该Agent从该功能标签的候选池中临时移除
  2. 移除时限：积累20条新数据后重新评估
  3. 不同功能标签独立判断（Agent A在"Prompt工程"被淘汰，不影响它在"LangChain组件"的遴选）
  4. 淘汰后的Agent进入离线评估队列（见5.5.2）

阈值调优计划：
  - 系统上线后，监控淘汰率
  - 目标淘汰率：5-10%（太高说明阈值太严，太低说明太松）
  - 用网格搜索确定最优阈值组合
```

### 2.4.4 早停机制

```
触发条件：连续2轮协作，
          所有候选Agent的 importance_score 波动 < 0.05

动作：本轮遴选提前结束，直接使用当前Top-1 Agent
目的：节省API调用，Agent之间已达成共识时不再强行迭代

早停与候选辩论的关系：
  早停场景下该段只有1个候选Agent，裁判团无法执行候选Agent辩论
  （辩论需要落选候选质疑+获胜候选辩护，见4.4.2节）。
  此场景裁判团直接进入分歧解决通道：
  - 3:0通过 → 正常放行（跳过辩论环节，日志标注"early_stop_skip_debate"）
  - 2:1分歧 → 仅执行第一层（裁判团分歧解决），跳过第二层（候选辩论）
  - 0:3全票失败 → 进入裁判长终审门控（同正常流程）
```

## 3.1 功能定义

Agent池负责根据学情诊断结果，生成准确的领域知识内容。核心原则是：**每个Agent有主功能（精），但面对任何问题都会输出（粗）**。通过对比多Agent输出，选出最优，确保输出质量。

> **表述澄清**：每个领域Agent是**同一LLM的不同Prompt角色实例**，差异来自System Prompt而非模型本身。这是多智能体协作的标准范式（MetaGPT论文亦采用此方式——同一模型扮演Product Manager/Architect/Engineer等不同角色）。Agent池的价值在于**Prompt专业化+动态遴选**，而非模型差异化——10个Agent在各自的功能标签上有不同擅长程度（per-tag importance_score），调度员根据学情画像匹配最合适的Agent组合。

## 3.4 候选输出机制

### 3.4.1 单领域问题（1段，2个候选Agent）

```
调度员输出：候选 = [Agent_X, Agent_Y]  （2个候选）

Agent_X输出答案 ┐
                ├→ 审核团队段内评选 → 最优Agent聚焦输出 → 裁判团
Agent_Y输出答案 ┘

※ 即便只有1个"最匹配"Agent，也必须补上次匹配Agent，确保有输出可比较
※ 单候选不跳过审核和裁判，完整流程必走
```

### 3.4.2 跨领域问题（2-3段，每段2个候选Agent）

```
调度员输出：
  第1段候选 = [Agent_X, Agent_Y]  （每段2个候选）
  第2段候选 = [Agent_A, Agent_B]

段1：Agent_X、Agent_Y分别输出 ┐
                               ├→ 审核团队段内评选 → 段1最优
段2：Agent_A、Agent_B分别输出 ┐
                               ├→ 审核团队段内评选 → 段2最优

→ 跨段一致性审查 → 各段最优拼接 → 聚焦输出 → 裁判团
```

**多段内容合并机制**：

多段场景下，聚焦输出和裁判裁决分别执行合并策略：

| 产物 | 合并策略 | 实现方式 |
|------|---------|---------|
| 多段聚焦输出 | 按段标注拼接 | conclusion→按[段1]/[段2]标注合并；reasoning_steps→按段分隔；knowledge_refs→直接拼接；code_example→用\n\n分隔；difficulty_note→按段标注 |
| 多段裁判裁决 | 取最严格结果 | 整体裁决优先级：FAILED > REVISE > LOW_CONFIDENCE_PASSED > PASSED；裁判意见按段[段1]/[段2]标注合并；验证率取平均；分歧解决记录取第一个非空 |

**设计理由**：各段内容独立，不适宜强制融合。按段保留标识既保证一致性又保证可追溯性。

### 3.4.3 全链路问题（3-5段，每段2个候选Agent）

```
调度员+学情诊断共同拆解问题：

原问题："从零开始做一个完整的AI应用"

拆解结果：
  第1段："理解LLM基本原理"           → 候选[Agent_1, Agent_2]
  第2段："设计Prompt"                → 候选[Agent_2, Agent_3]
  第3段："搭建RAG架构"             → 候选[Agent_4, Agent_8]
  第4段："部署上线"                → 候选[Agent_9, Agent_10]

各段候选分别输出 → 审核团队段内独立评选（每段独立）
→ 跨段一致性审查 → 拼接 → 聚焦输出 → 裁判团
```

### 3.4.4 候选自评估机制（DyLAN真正落地）

> **设计依据**：DyLAN论文核心发现——Agent应根据当前任务动态评估自身相关性，不相关的Agent主动退出，而非仅靠历史分数被动遴选。当前方案的importance_score是"过去表现"（历史分），缺少"当下判断"（任务级自评估）。两者结合才是DyLAN的完整动态选择。

**机制设计**：

每个候选Agent在输出答案的同时，额外输出一个 `self_confidence` 字段，在同一轮LLM调用中完成，不额外增加调用次数。

```json
{
  "answer": { ...FocusedOutput... },
  "self_confidence": {
    "score": 0.85,
    "weak_points": ["对LangChain v0.3的新API不确定", "代码示例未验证过"]
  }
}
```

**自评估规则**：

| 规则 | 说明 |
|------|------|
| 诚实评估 | Agent被要求诚实评估：如果问题涉及secondary_functions，confidence应≤0.7 |
| 双低触发RAG | 如果两个候选的self_confidence都<0.5 → 触发知识库RAG增强（给两个Agent补充检索结果后重新生成） |
| 不直接计入评分 | self_confidence不直接计入审核团队评分公式，但通过双低RAG触发机制间接影响评分输入——当两个候选self_confidence都<0.5时触发RAG增强，RAG增强后的输出是新的一次完整流程，审核团队评分的是新输出而非旧输出 |
| 历史追踪 | self_confidence写入贡献记忆，用于追踪Agent的自评估校准度（是否overconfident/underconfident） |

> **阈值选择说明**：0.5阈值意味着"只有当两个候选都对自己的输出不太有信心时才触发RAG增强"，避免单候选信心不足但另一候选信心充足时浪费RAG调用。0.5是基于DyLAN论文实验的经验值，系统上线后可实测调整（如降低至0.4以增加触发频率，或提高至0.6以减少RAG调用）。

**与importance_score的关系**：

```
importance_score = 历史表现分（调度员用于遴选候选）
self_confidence  = 当下任务分（系统用于判断是否需要RAG增强）

两者结合 = DyLAN完整动态选择：
  调度员用importance_score选"过去表现好的Agent"
  系统用self_confidence判断"这次它是否真的擅长"
  例：Agent_3在RAG架构上importance_score=0.89（历史强），
      但本次问题涉及RAG+向量数据库跨域，Agent_3自评confidence=0.6（不确定向量库部分）
      → 系统知道需要在向量库维度补充验证
```

**额外调用**：0次（自评估在同一轮LLM调用中输出）

## 3.5 聚焦输出Schema（正式定义）

最优Agent被选中后，进行聚焦输出。**实现方式**：

1. **不是重新生成**，而是在原有会话中继续（同一LLM会话，保持上下文）
2. **Prompt设计**（含审核反馈回流，MAR真正落地）：

> **设计依据**：MAR论文核心发现——单Agent输出存在确认偏误，反思后改进能显著提升质量（Pass@1提升3-5%）。当前方案的审核反馈只用于"选谁赢"，浪费了反馈的诊断价值。反馈回流后，聚焦输出不再是"格式化补全"，而是"有针对性的改进"。

```
【系统通知】
你在段内评选中获胜。以下是审核团队对你输出的具体反馈，请针对改进。

你的原始输出：
{原始输出JSON}

审核反馈（具体问题，不含评分）：
  Verifier反馈：{fact_accuracy发现的具体问题，如"第2条知识点缺少知识库依据"}
  Skeptic反馈：{logic_completeness发现的具体问题，如"步骤3到步骤4缺少过渡逻辑"}
  Evaluator反馈：{pedagogical_fit发现的具体问题，如"对入门学生使用了未解释的术语"}

请按以下要求改进：
1. 针对审核反馈中的每个问题进行修正，并标注哪些地方做了修改
2. 确认conclusion是否准确（1-2句话）
3. 补充reasoning_steps中缺失的步骤（至少3步）
4. 为每条知识点添加knowledge_refs（知识库依据）
5. 明确applicable_conditions（适用条件）
6. 如有代码操作，提供code_example
7. 根据学生水平添加difficulty_note

输出必须严格按FocusedOutput Schema。
```

**反馈回流规则**：
- 审核团队只传"具体问题"给Agent，**不传评分数字**（防止Agent只追求分数）
- 如果审核团队没有发现问题（3人全高分），聚焦输出走原始流程（确认+完善，不传反馈）
- 这不是"退回修改"，是"赢者精进"——Agent知道赢了，但还知道哪里可以更好

3. **质量控制**：
   - 如果"改进"后引入新错误，裁判团会检测到
   - 聚焦输出最多尝试2次，仍不合格则退回修改

**聚焦输出Schema**（严格JSON格式）：
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "FocusedOutput",
  "type": "object",
  "required": ["conclusion", "reasoning_steps", "knowledge_refs", "applicable_conditions"],

### 3.5.1 自动验证

Agent填完Schema后，系统自动执行三项检查（不需要人工）：

| 检查项 | 验证方式 | 不合格处理 |
|--------|---------|-------------|
| Schema完整性 | JSON Schema校验（程序化） | 缺必填字段 → 退回Agent补填（最多2次） |
| 引用可溯源性 | 对`knowledge_refs`每条去向量库检索验证 | 无依据 → 标记为"待验证"，不强制退回 |
| 代码安全检查 | AST静态分析（ast.parse + 危险操作检测） | 检测到危险操作（eval/exec/subprocess等）→ 在原输出末尾追加安全检查警告，不阻断流程 |

**代码安全检查方式**：

采用**Python AST静态分析**替代沙箱执行。理由：
1. 沙箱执行耗时长（需docker容器+依赖安装），会显著增加响应延迟
2. AST分析无需执行代码即可检测语法错误和危险操作（eval/exec/subprocess/open/requests等），安全且即时
3. 危险操作不自动阻断（qwen-max/DeepSeek生成的代码含敏感操作不一定恶意，可能是教学所需），以警告形式追加到生成的文档中，提醒学生注意

检查过程（代码实现）：
```python
def check_code_in_markdown(markdown_text: str) -> str | None:
    """提取markdown中所有代码块，逐块做AST语法检查 + 危险操作检测
    
    危险操作黑名单：
      - ast.Call: func.id in ['eval', 'exec', 'compile', '__import__']
      - ast.Attribute: attr in ['subprocess', 'Popen', 'run', 'call', 'check_call']
    返回：问题描述字符串（无问题返回None）
    """
    for code_block in extract_code_blocks(markdown_text):
        tree = ast.parse(code_block)  # 语法检查
        dangerous = detect_dangerous_calls(tree)
        if dangerous:
            return f"检测到危险操作: {', '.join(dangerous)}"
    return None
```

**退回修改最多2次**，2次仍不合格则直接输出，携带"低置信度"标记交给裁判团处理。

### 3.5.2 JSON输出质量控制——三层兜底机制

> LLM输出严格JSON Schema存在一定失败率。6个SOP阶段每个都依赖JSON输出，串联后单靠重试不可靠。本方案采用**三层兜底**而非无限重试——工程确定性修复优先于LLM重试。

**三层兜底架构**：

```
共享JSON校验服务（所有Agent输出统一经过此服务）：

第一层：原生约束（成本：0，延迟：0，覆盖率：~85%）
  → 使用 qwen-max/DeepSeek 的 response_format 模式（OpenAI-compatible）
    · qwen-max: response_format={type:"json_schema", schema:{...}}
    · DeepSeek-V3: response_format={type:"json_object"}
  → 原生约束比Prompt指令稳定得多，解决大部分格式问题

第二层：正则修复（成本：0，延迟：<1ms，覆盖率：追加~10%）
  → 提取最外层 {...} JSON块
  → 字段级校验：required字段缺失 → 填Schema定义的默认值
  → 类型校验：number字段收到string → 尝试parseFloat
  → 枚举校验：role字段不在白名单 → 设为默认值

第三层：LLM修复（成本：1次额外调用，延迟：+2-3s，覆盖率：追加~3-5%）
  → 仅当前两层都失败时触发
  → 发送原始输出 + Schema + 具体错误信息，要求重新生成
  → 仅重试1次

最终预期合格率：≥97%
```

**降级策略**（第三层修复仍失败时）：
- 学情诊断失败 → 使用默认全领域画像
- 聚焦输出失败 → 使用广度优先输出（不做聚焦合并）
- 审核阶段失败 → 跳过审核，标记"未审核"
- 裁判阶段失败 → 取原始候选最高分直接输出，标记"低置信度"
- 资源生成失败 → 仅返回讲义（核心资源），实操和试题降级为"生成失败，请重试"

> **设计理由**：降级要打log并通知用户，但比卡死/报错好100倍。评审演示时，降级路径的存在本身就是工程完备性的体现。

## 3.6 资源生成Agent——3种形态实现

> 对齐赛题要求：**"动态生成包含定制化资源、实操指南、分阶测试题等至少3种形态的个性化学习资源"**。

### 3.6.1 触发时机与条件判断

裁判团对聚焦输出做出"通过"裁定后，资源生成Agent介入。

> **代码实践验证：三种形态均始终生成**。实操指南和分阶测试题的原条件触发条件（code_example非空、question_type白名单）已在实现中放宽为始终生成，由LLM Prompt自适应内容形态。概念类问题同样需要操作指引（决策清单、应用检查表），调试排错类同样需要测试题（找错题、综合分析题）。实现确保`practice_guide`和`quiz`字段始终非null，降低学生收到空资源概率。

| 形态 | 触发条件 | 说明 |
|------|---------|------|
| **定制化讲义** | **必选**（始终生成） | 基础形态，几乎是格式化输出，API成本低 |
| **实操指南** | **始终生成**（含代码→代码实操步骤；无代码→决策检查清单/应用步骤） | 概念类问题同样需要操作指引（评估步骤、落地路线图），放宽条件后学生始终收到可操作的步骤化内容 |
| **分阶测试题** | **始终生成**（根据question_type自适应题型） | 调试排错类转找错题，全链路规划类转综合分析题，确保学生始终有自测手段 |

### 3.6.2 三种形态详细设计

**形态1：定制化讲义**

```
输入：聚焦输出JSON + 学情画像
输出格式：Markdown文档

内容结构：
  - 标题（针对学生问题）
  - 核心结论（conclusion字段）
  - 分步讲解（reasoning_steps字段，每步展开讲解）
  - 知识来源标注（knowledge_refs字段，链接至知识库文档）
  - 难度说明（difficulty_note字段）
  - 适用条件（applicable_conditions字段）

个性化适配：
  - 入门水平：每步后加"通俗理解"段落
  - 中级水平：保留专业术语，加简要解释
  - 进阶水平：增加"底层原理"扩展段落
```

**形态2：实操指南**

```
输入：聚焦输出JSON（含code_example字段）+ 学情画像
输出格式：Markdown文档（含代码块）

内容结构：
  - 目标说明
  - 环境准备（根据学生background字段调整）
  - 步骤化操作（reasoning_steps字段转化为操作步骤）
  - 完整代码示例（code_example字段，加上必要import和注释）
  - 预期输出
  - 常见问题排查（针对该知识点的高频报错）

个性化适配：
  - 无编程背景：增加环境安装详细步骤
  - 有Python基础：跳过基础环境配置
  - 有ML基础：增加参数调优说明
```

**形态3：分阶测试题**

```
输入：聚焦输出JSON + 学情画像
输出格式：JSON（结构化试题）

生成规则：
  - 题目数量：3-5道（根据知识点复杂度调整）
  - 难度阶梯：
      第1题：直接对应reasoning_steps中的某一步（基础巩固）
      第2题：跨步骤综合（应用能力）
      第3题及以上：加入干扰项或边界条件（进阶挑战）
  - 题型：
      knowledge_level=入门 → 判断题+选择题
      knowledge_level=中级 → 选择题+简答提示题
      knowledge_level=进阶 → 代码补全题+设计分析题

每题结构：
  {
    "question": "问题文本",
    "type": "判断/选择/简答/代码补全",
    "options": ["A...", "B...", ...],  // 仅选择题有
    "answer": "正确答案或答题提示",
    "explanation": "解析，引用知识库依据",
    "difficulty": "基础/应用/进阶"
  }
```

### 3.6.3 3种形态的生成顺序

```
同一知识点，资源生成Agent按顺序生成：
  第1步：定制化讲义（必选，最基础，几乎是格式化输出）
  第2步：实操指南（条件触发，需要理解code_example字段）
  第3步：分阶测试题（条件触发，需要理解知识点逻辑才能出题）

生成后打包为1个ZIP或直接分Tab展示给学生
```

### 3.6.4 降维解释与进阶挑战动态追加（对齐赛题要求(3)②）

> 赛题原文：*"根据答题正确率，多智能体协同决策是否对知识点进行'降维解释'或生成'进阶挑战任务'"*

**降维解释机制**：当答题正确率低或学生反馈"难度不匹配"时，资源生成Agent重新生成同一知识点，但使用降维策略而非原Prompt。

```
降维Prompt模板（资源生成Agent降维模式）：

输入：
  原FocusedOutput JSON + 学情画像 + 降维原因（答题正确率<60% / 学生反馈难度不匹配）

降维规则（根据knowledge_level选择降维策略）：
  入门水平降维：
    - 每步推理加生活类比（"就像XX一样..."）
    - 删除未解释的专业术语，用日常语言替代
    - 将5步推理拆为8小步，每步加"为什么这样？"引导问题
    - 代码示例加逐行注释，解释每一行的作用

  中级水平降维：
    - 加过渡概念解释段落（"在理解XX之前，你需要先知道YY..."）
    - 补"前置知识回顾"段落（3-5行简述必要前置知识）
    - 复杂推理链拆为子步骤，每2步加验证节点

  进阶水平降维：
    - 复杂多步推理拆为子问题链，每步独立可验证
    - 加中间验证节点（"到这里你可以先验证：XX应该等于YY"）
    - 减少省略步骤，补充推导细节

输出：降维版讲义/实操指南/测试题（同FocusedOutput Schema，但difficulty_note标注"降维版"）
```

**进阶挑战动态追加**：当答题正确率≥85%时，从原有3题追加1道动态进阶题。

```
进阶挑战追加规则：

触发条件：分阶测试题答题正确率≥85%

追加策略：
  - 题目难度：从"应用"级升至"分析/设计"级
  - 知识范围：将当前知识点与相邻知识点组合（跨知识联动）
    例如：原知识点"RAG检索" → 进阶题"RAG检索+向量数据库选型的联合决策"
  - 题型升级：
    入门→选择题改为需要自主推理的简答提示题
    中级→简答提示题改为代码补全或方案设计题
    进阶→追加开放性分析题（"对比三种方案的优劣并给出选择理由"）
  - 干扰项增强：加入真实场景的边界条件（如中文长文档检索、多模态数据）

输出：追加1道进阶题，打包到原测试题集合中交付
```

# 第四部分：模块三——审核团队 + 裁判团

> 对齐赛题术语：**"校验-决策"阶段**，对应赛题所述"内容审核与纠偏Agent"。

## 4.0 模块输入输出规格

**输入**：
- `segments: list[dict]` — 来自模块二（3.4节）的候选输出
  ```python
  [{"seg_id": "seg_1", "outputs": [{"agent_id": "Agent_1", "output_json": ...}]}]
  ```
- `focused_output: dict | None` — 聚焦输出（来自模块二3.5节），审核阶段为None
- `StudentProfile: dict` — 学情画像（来自模块一2.2节）

**输出**：
- 审核团队阶段：`ReviewFeedback` JSON（每段最优Agent+评分+具体问题列表，见6.2.2节Schema）
  ```python
  {"seg_id": "seg_1", "candidates": [{"agent_id": "Agent_4", "scores": {"fact_accuracy": 0.9, "logic_completeness": 0.85, "pedagogical_fit": 0.88}, "issues_found": [...], "is_winner": true}, ...]}
  ```
- 裁判团阶段：`JudgeVerdict` JSON（裁决结果+分歧解决记录+候选辩论记录+溯源标注，见6.2.3节Schema）
- 溯源标注：包含在JudgeVerdict JSON的`traceability`字段中（见4.4.4节）

**处理逻辑摘要**：
1. 审核团队：3人独立评分（Verifier事实/Skeptic逻辑/Evaluator适配）→ 段内独立评选 → 跨段一致性审查（4.3节）→ 审核反馈结构化为ReviewFeedback JSON
2. 裁判团：3人独立裁决（事实审查/逻辑审查/适用性审查）→ 分歧解决DISSENT_RESOLVE（4.4.2节）→ 候选Agent辩论（2:1分歧时触发）→ 反向怀疑（条件触发，4.4.3节）
3. 修改重审：修改后3名裁判全部重审（非仅异议裁判）

> 本模块**只负责评分和裁决**，不生成内容、不调度Agent。审核团队回答"谁最好"，裁判团回答"够不够好"。

## 4.1 功能定义

本模块由两支独立团队组成：
- **审核团队**（3人）：对候选Agent的输出进行段内评选，选出最优；多段场景下执行跨段一致性审查。
- **裁判团**（3人）：对最优Agent的聚焦输出进行分歧解决、候选Agent辩论和溯源标注，做出最终裁定。

两支团队职责边界清晰：
- 审核团队回答的问题是：**"候选Agent中谁的输出质量最高？"**（相对比较）
- 裁判团回答的问题是：**"最优Agent的输出是否足够好，能否直接给学生？"**（绝对质量判断）

## 4.2 审核团队详细设计

### 4.2.1 三人Persona定义

| 角色 | Persona | 锚定物 | 评分维度 |
|------|---------|--------|---------|
| **Verifier** | 事实核查员 | 知识库检索结果（逐条核对） | `fact_accuracy`（事实准确率） |
| **Skeptic** | 逻辑挑刺者 | 检查清单（5条，见下文） | `logic_completeness`（逻辑健全性） |
| **Evaluator** | 教学适配评估员 | 学情画像JSON对象（逐字段对照） | `pedagogical_fit`（教学适配度） |

### 4.2.2 Verifier——事实核查详细规则

**锚定方式**：将Agent输出切分为若干知识点陈述，对每个陈述去向量知识库检索Top-3相关片段，对比一致性。

```
Verifier的评分Prompt核心结构：

以下答案的每条知识点，请去知识库检索验证：
  知识点1："..." → 检索结果：[Top-3片段] → 一致/矛盾/无法确认
  知识点2："..." → ...

请输出严格JSON：
{
  "fact_accuracy": 0.0-1.0,  // 可验证且正确的知识点占比
  "verified_count": 已验证数量,
  "contradiction_count": 矛盾数量,
  "unverified_items": ["无法确认的知识点1", ...],
  "contradiction_items": ["矛盾的知识点1", ...]
}
```

### 4.2.3 Skeptic——检查清单详细规则

**锚定方式**：过5条固定检查清单，每条通过得0.2分，总分1.0。**不依赖LLM自由判断**。

```
检查清单（固定，不允许LLM自创）：

清单1：每一步推理是否给出了原因？
  → 如果某一步以"因此..."开头但没有前文，不通过

清单2：结论是否和前面的推理一致？
  → 如果推理说"不推荐X"，结论说"推荐使用X"，不通过

清单3：有没有遗漏已知的前置条件？
  → 如果答案涉及"安装LangChain"但没有提Python版本要求，不通过

清单4：是否存在循环论证？
  → 如果A证明B，B又证明A，不通过

清单5：关键步骤是否可执行（如果是操作步骤类问题）？
  → 如果某步骤说"配置好环境"但没有说怎么配置，不通过

评分：每条通过→+0.2；不通过→0；部分通过→+0.1
```

### 4.2.4 Evaluator——教学适配评估详细规则

**锚定方式**：对照学情画像JSON对象的每个字段，逐条评估输出适配度。

```
Evaluator的评分Prompt核心结构：

学情画像：{学情画像JSON}
Agent输出：{输出内容}

请逐条评估：

1. knowledge_level匹配度（0.0-1.0）：
   输出难度是否匹配学生的knowledge_level？
   （入门水平 → 输出不应出现未解释的专业术语）

2. background适配度（0.0-1.0）：
   输出是否考虑了学生的background？
   （文科背景 → 输出应多用类比，少用代码）

3. goal对齐度（0.0-1.0）：
   输出是否朝着学生的current_goal方向？
   （快速上手 → 输出应侧重操作步骤，而非底层原理）

4. 可操作性（0.0-1.0）：
   学生能否根据输出直接执行？

输出JSON：
{
  "pedagogical_fit": (4个维度平均分),
  "dimension_scores": {"level_match": ..., "bg_fit": ..., "goal_align": ..., "actionability": ...},
  "mismatch_details": ["具体不匹配之处"]
}
```

### 4.2.5 段内评选汇总规则

```
综合得分 = fact_accuracy × w1 + logic_completeness × w2 + pedagogical_fit × w3
```

**权重配置**（存储在`system_config`表，可通过管理后台调整）：
- **初始默认值**：w1=0.35, w2=0.35, w3=0.30
- **权重调整建议**：
  - 入门水平学生：w3权重可稍高（教学适配更重要）
  - 进阶水平学生：w1权重可稍高（事实准确性更重要）
- **优化计划**：系统上线后，用A/B测试确定最优权重
  - 测试1：w1=0.5, w2=0.3, w3=0.2（偏重事实准确性）
  - 测试2：w1=0.3, w2=0.4, w3=0.3（偏重逻辑健全性）
  - 测试3：w1=0.3, w2=0.3, w3=0.4（偏重教学适配度）

### 4.2.6 审核团队意见冲突解决

**核心原则：有锚定依据的意见自动生效，三人意见冲突时以Verifier（事实准确性）权重最高。**

```
审核完成后汇总的决策流程：

1. Verifier发现事实矛盾 → 有知识库检索依据 → 自动生效，对应Agent扣分
2. Skeptic发现逻辑问题 → 对应检查清单条目 → 自动生效，对应Agent扣分
3. Evaluator发现教学适配问题 → 对照学情画像字段 → 自动生效，对应Agent扣分
4. 三人意见冲突（例如Verifier给高分，Skeptic给低分）→ 以综合得分决定最优，
   不另引入外部裁量者
```

> **注意**：调度员不参与审核阶段的意见冲突解决。审核团队本身就是独立裁决机构，三人评分加权汇总即可决定段内最优。

## 4.3 跨段一致性审查（多段场景）

> 触发条件：问题复杂度为"跨领域"或"全链路"，即输出由多段拼接而成。

### 4.3.1 审查流程

审核团队完成**段内独立评选**后，自动进入跨段一致性审查。

**调用策略（优先少调用）**：

| 情形 | 处理方式 | 额外调用 |
|------|---------|---------|
| 原有评分Prompt容量 < 80% | 在Prompt末尾追加审查任务，合并输出 | **0次** |
| 原有Prompt已满（>80%）| 单独发起1次审查调用 | **1次** |
| 审查发现矛盾需修改 | 触发4.3.3冲突修改规则，可能再增加1次 | **最多2次** |

> **修正说明**：之前声称"不增加额外LLM调用"过于绝对。实际上，当Prompt容量充裕时可以做到不增加调用；当Prompt已满时允许额外增加1次专用审查调用，整体调用量增加 < 5%，可接受。

**审查方式（Prompt末尾追加）**：
   - Verifier：追加"请检查各段知识点是否矛盾"
   - Skeptic：追加"请检查段间衔接是否连贯"
   - Evaluator：追加"请检查各段难度是否跳变"

**输出合并**：审查结果合并到原评分JSON中

**示例（Verifier Prompt新增任务）**：
```
【原有任务】核查以下答案的事实准确性...
【新增任务】检查各段知识点是否矛盾：
  段1知识点：...
  段2知识点：...
  如果有矛盾，请在contradiction_items中标注。
```

> **关键修正**：跨领域问题中，每段是独立评选的（段1候选只和段1候选比，不和段2候选比）。跨段一致性审查是在各段选完最优之后，检查段间衔接，不是跨段比较Agent输出。

| 审查员 | 审查维度 | 锚定方式 |
|--------|---------|-----------|
| Verifier | 事实矛盾：相邻段的知识点是否矛盾 | 抽取各段关键知识点陈述，交叉核对 |
| Skeptic | 逻辑断裂：段间衔接是否连贯 | 过3条衔接检查清单（见下文） |
| Evaluator | 难度跳变：各段难度是否和学生水平匹配 | 对照学情画像，逐段评估 |

### 4.3.2 衔接检查清单（Skeptic专用）

```
衔接清单1：前后段术语是否一致？
  → 第1段用"Retriever"，第2段用"检索器"，可接受（补充映射）
  → 第1段用"Retriever"，第2段用"Receiver"，不可接受（矛盾）

衔接清单2：第N段的开头是否承接第N-1段的结尾？
  → 若第N-1段结尾引出概念Y，第N段开头应提及Y或明确说明为何不提

衔接清单3：步骤编号是否连续？
  → 各段独立编号容易造成混淆，需统一编号
```

### 4.3.3 冲突修改规则

```
发现冲突后：
  1. 定位冲突位置（哪段的哪一句）
  2. 判断冲突类型：
     - 事实矛盾 → 由Verifier指定相关Agent修改
     - 逻辑断裂 → 由Skeptic指定相关Agent补充衔接语
     - 难度跳变 → 由Evaluator指定相关Agent调整难度表述
  3. 修改范围判定：
     - 只改冲突的一句或几句话 → 小改 → 不需再过裁判团
     - 改核心结论或新增知识点 → 大改 → 必须再过裁判团
  4. 修改次数上限：每轮最多修改2次（含小改+大改）
```

## 4.4 裁判团详细设计

### 4.4.1 三人分工（与审核团队不同Persona）

| 裁判 | Persona | 审查重点 | 裁判团中的独特作用 |
|------|---------|---------|-------------------|
| **裁判1（事实审查）** | 知识库对照专家 | 每条知识点有没有溯源依据 | 分歧解决僵持时的最终裁决者（事实准确性优先级最高） |
| **裁判2（逻辑审查）** | 推理链完整性专家 | 步骤之间有没有跳跃、矛盾 | 对应MAR论文"Logician"Persona |
| **裁判3（适用性审查）** | 学生适配专家 | 输出给这个学生用合不合适 | 防止"准确但不适合"的答案通过 |

**核心设计原则（来自Debate论文）**：
- 三人**独立审查**，互不可见对方的判断和自信度（防止锚定效应）
- 裁判团**不看到**审核团队给出的review_score（防止先入为主）
- 裁判团**只看到**：聚焦输出JSON + 学情画像 + 知识库检索接口

### 4.4.2 分歧解决状态机（完整版）

> **设计依据**：Debate论文核心发现——辩论的价值在于MaW→C转化（多数错误时少数纠正多数），关键条件是少数方必须看到多数方的论证后才能有效反驳。原方案将2:1拆为DEBATING和PROTECTING两条路径，但2:1和1:2本质是同一局面（多数2票对少数1票），PROTECTING为死路径。现合并为统一的分歧解决机制，并新增候选Agent辩论层——让真正懂领域的内容生产者参与交叉验证。

```
状态定义：
  [REVIEWING]  →  三人独立审查（并行，互不可见）
       ↓
  [COMPARING]  →  汇总三人判断
       ↓
       ├─ 3:0 全票通过 → [PASSED] → 溯源标注 → 最终输出
       └─ 2:1 分歧    → [DISSENT_RESOLVE] → 分歧解决（统一路径）
                              ↓
                    ┌─── 第一层：裁判团分歧解决 ───┐
                    │                              │
                    │  少数方（1人）提交书面证据：    │
                    │    证据类型1：知识库检索结果     │
                    │    证据类型2：检查清单条目       │
                    │    证据类型3：学情画像字段       │
                    │                              │
                    │  多数方（2人）必须回应：        │
                    │    接受证据 → 改判 → [REVISING]│
                    │    反驳证据 → 维持原判          │
                    │                              │
                    │  若双方僵持：                  │
                    │    → 裁判1（事实审查）最终裁决  │
                    │    （事实准确性优先级最高）      │
                    └──────────────────────────────┘
                              ↓
                    ┌─── 第二层：候选Agent辩论 ────┐
                    │  （与第一层并行触发）            │
                    │                              │
                    │  裁判团分歧中的少数方观点        │
                    │  被 anonymized 传给候选Agent：  │
                    │                              │
                    │  落选候选Agent收到质疑：        │
                    │    认同 → 提交补充证据          │
                    │    不认同 → 提交反驳证据        │
                    │                              │
                    │  获胜候选Agent收到同样的质疑：   │
                    │    必须提交辩护证据             │
                    │                              │
                    │  两方证据合并提交给裁判团       │
                    │  作为分歧解决的额外输入         │
                    └──────────────────────────────┘
                              ↓
                    ┌─── 辩论证据消费路径 ─────────┐
                    │                              │
                    │  辩论证据与少数方举证合并后，   │
                    │  裁判团3人全部重新审查：        │
                    │    不只看多数/少数方的原证据，   │
                    │    还要看候选Agent辩论证据      │
                    │                              │
                    │  消费方式：                    │
                    │    1. 辩论证据追加至裁判审查     │
                    │       Prompt中，作为"第三方     │
                    │       专家意见"                │
                    │    2. 3名裁判独立评估辩论证据    │
                    │       是否揭示真实问题          │
                    │    3. 若辩论证据揭示实质问题     │
                    │       → 判定"证据充分"         │
                    │       → 退回Agent修改           │
                    │       → 进入[REVISING]          │
                    │    4. 若辩论证据不充分           │
                    │       → 判定"证据不足"         │
                    │       → 维持原判[PASSED]        │
                    └──────────────────────────────┘
                              ↓
                    分歧解决结果：
                      证据充分 → [REVISING] → 退回Agent修改
                      证据不足 → [PASSED] → 溯源标注 → 最终输出
         
  [REVISING] 状态：
       Agent修改后，3名裁判全部重新审查（非仅提出异议的裁判）
       → 3:0 → [PASSED]
       → 仍有异议 → 回到[COMPARING]，但修改次数+1
       → 修改达到2次上限 → 标注"低置信度"强制通过

  **0:3全票失败 → 裁判长终审门控**：
       \> 0:3在原方案状态机中未定义路径（DISSENT_RESOLVE只处理2:1）。
       \> 终审门控规则：
       \>   裁判长（事实审查裁判）做最后一次评估：
       \>     内容是否达到最低可接受标准？
       \>     达到 → 标注LOW_CONFIDENCE_PASSED + "终审挽救"，正常降级放行
       \>     未达到 → 仍放行（竞赛要求不能拒绝学生），但标注"unanimous_fail_force_pass"强制放行标记
       \>   设计意图：终审门控确保大部分0:3被挽救（改判），只有终审也确认不行的才标记强制放行 → 真正的强制放行极少
       \> 终审Prompt模板见[附录：全票失败终审Prompt](./#全票失败终审Prompt)
```

**候选Agent辩论的设计理由（Debate论文真正落地）**：

| 维度 | 原方案（贴标签） | 改进后（真落地） |
|------|----------------|----------------|
| 辩论参与者 | 裁判之间辩论（外行审查内行） | 候选Agent之间辩论（内容生产者交叉验证） |
| 触发条件 | 2:1分歧触发DEBATING或PROTECTING | 2:1分歧统一触发DISSENT_RESOLVE，同时触发候选辩论 |
| MaW→C转化路径 | 无（PROTECTING是死路径） | 落选候选可能看到获胜者没看到的问题，用证据说服多数方 |
| 落选Agent利用 | 完全浪费 | 落选候选的专业知识被用于交叉验证 |
| 额外调用 | 0 | +1-2次（仅2:1分歧时触发，约30%场景） |

> **修正说明**：原方案DEBATING和PROTECTING基于2:1和1:2分别触发，但两者本质是同一局面（多数2票对少数1票），PROTECTING为死路径。现合并为统一的DISSENT_RESOLVE路径，并新增候选Agent辩论层，让真正懂领域的内容生产者参与交叉验证。修改后的输出由3名裁判全部重审。

### 4.4.3 反向怀疑机制（来自Debate论文"强模型悖论"）

**问题**：Debate论文发现，强模型提供高质量推理时，队友的纠正率反而更低（80% vs 弱模型93%）。原因是队友盲从强模型的输出。

**本方案解法**：

裁判团在审查时，**不看到审核团队的排名或评分**，但裁判团可以通过输出内容本身感知质量差异。为防止对"看起来很好"的输出盲从，裁判团自动对**输出内容特征**触发更严格的审查：

```
反向怀疑触发规则（基于输出内容特征，不依赖审核团队排名）：

触发条件（满足任一即触发严格审查）：
  1. 输出中knowledge_refs数量 ≥ 12条（信息密度高，易隐藏错误）
  2. 输出中code_example字段存在且代码行数 ≥ 50行（复杂代码更易含bug）
  3. 输出中reasoning_steps ≥ 20步（推理链越长，出错概率越高）

严格审查标准（触发后自动启用）：
  标准1：证据要求更严
    → 触发严格审查的输出，整体可溯源率需≥80%才通过（不再0容忍，避免少量综合推理步无单一外部文档而误降级）
    → 未触发的输出，可接受最多1条"待验证"
    
  标准2：逻辑审查更细
    → 触发严格审查的输出，Skeptic检查清单5条全部必须0.2分通过
    → 未触发的输出，允许1条0.1分（部分通过）
```

> **修正说明**：① 原方案使用"审核团队排名第1"作为触发条件，但裁判团按规定不可见review_score，形成逻辑矛盾。改为基于输出内容特征触发，裁判团无需任何外部信息即可独立判断是否启用严格审查。② 阈值校准（2026-08-15）：原 refs≥5/代码≥20行/步骤≥8 过低，导致大量中等复杂度输出误触严格模式并要求100%溯源，过度降级为低置信放行；上调为 refs≥12/代码≥50行/步骤≥20，且溯源要求从"100%可溯源(0容忍)"放宽到"整体可溯源率≥80%才通过"。
>
> **与候选辩论的协同**：反向怀疑是"被动触发"（基于输出特征），候选Agent辩论是"主动质疑"（基于内容生产者交叉验证）。两者互补：反向怀疑防止"看起来很好的输出"被盲从，候选辩论让真正懂领域的人参与质疑。

### 4.4.4 高保真知识溯源标注

> 对齐赛题要求：**"实现高保真知识溯源与约束生成"**。

裁判团做出"通过"裁定后，由裁判1（事实审查）执行溯源标注：

```
溯源标注格式（在最终输出JSON中增加字段）：

{
  ...,
  "traceability": [
    {
      "statement": "ConversationBufferMemory适用于保留完整对话历史",
      "source": "LangChain官方文档 v0.2 - Memory章节",
      "verification_status": "已验证 / 待验证 / 矛盾"
    },
    ...
  ],
  "overall_verification_rate": 0.94,
  "verdict": "passed / revise / low_confidence_passed / failed"
}
```

> **精简说明**：溯源标注中不再包含`retrieved_snippet`（知识库原文片段），避免最终输出体积过大。裁判1的溯源验证过程在服务端日志中完整记录，前端展示时仅显示`source`和`verification_status`。

## 4.5 辩论机制总结（对齐赛题"辩论与交叉验证"）

> 赛题原文："探索多智能体间的创新协同架构（如引入'辩论与交叉验证'机制以消除大模型在专业领域的'幻觉'）"

本方案的辩论与交叉验证机制采用**两层辩论 + 三重交叉验证**架构：

| 赛题术语 | 本方案对应实现 | 所在章节 |
|---------|-------------|---------|
| 辩论机制（第一层） | 裁判团分歧解决（DISSENT_RESOLVE：少数方举证→多数方回应→裁判长裁决） | 4.4.2 |
| 辩论机制（第二层） | **候选Agent辩论**（落选候选质疑+获胜候选辩护，内容生产者交叉验证） | 4.4.2 |
| 交叉验证 | 三重交叉验证（审核团队3人+裁判团3人+贡献记忆闭环） | 4.5 本节 |
| 消除幻觉 | 候选辩论（主动质疑）+ 反向怀疑（内容特征触发）+ 高保真溯源 | 4.4.2 + 4.4.3 + 4.4.4 |
| 约束生成 | 聚焦输出Schema约束 + SOP中间产物链 + 自动验证 | 3.5 + 6.2 |

### 两层辩论详细解释

```
第一层辩论：裁判团分歧解决
  - 触发：裁判团3人独立审查后出现2:1分歧
  - 流程：少数方提交书面证据 → 多数方必须回应 → 僵持时裁判长裁决
  - 作用：裁判层面的交叉验证，防止多数方盲通过

第二层辩论：候选Agent辩论（Debate论文核心落地）
  - 触发：与第一层并行，当裁判团出现2:1分歧时同时触发
  - 流程：
    1. 裁判团少数方观点被 anonymized 传给落选候选Agent
    2. 落选候选Agent认同或反驳质疑，提交证据
    3. 获胜候选Agent必须针对质疑提交辩护证据
    4. 两方证据合并提交给裁判团
  - 作用：让真正懂领域的内容生产者参与辩论（MaW→C转化路径）
  - 额外调用：+1-2次（仅约30%场景触发）
```

### 三重交叉验证详细解释

```
第一重交叉验证：审核团队段内评选
  - 3人对同一批候选输出独立评分
  - 评分锚定不同（知识库/检查清单/学情画像）
  - 结果：选出最优Agent

第二重交叉验证：裁判团独立裁决 + 候选Agent辩论
  - 3人对同一份聚焦输出独立审查
  - 互不可见，防止锚定
  - 2:1分歧时触发候选Agent辩论（内容生产者层面交叉验证）
  - 结果：通过/修改通过/低置信度通过/未通过

第三重交叉验证：贡献记忆闭环反馈
  - 将本次裁判团的verdict反馈至Agent的表现标签（per-function-tag粒度）
  - 多次被"退回修改"的Agent，下次遴选时importance_score降低
  - 结果：系统整体质量随时间提升
```

# 第五部分：贡献记忆与闭环优化

## 5.0 模块输入输出规格

**输入**：
- `agent_id: str` — Agent ID（来自模块二/三）
- `function_tag: str` — 功能标签（primary_function 或 secondary_functions 中的一项）
- `review_score: float` — 审核团队评分（0-1，来自模块三）
- `referee_verdict: str` — 裁判团裁决（英文枚举值：passed/revise/low_confidence_passed/failed，来自模块三）
- `student_feedback: dict | None` — 学生反馈（可选，来自前端）

**输出**：
- `updated_importance_score: float` — 更新后的贡献记忆分（写入 `agent_performance` 表）
- `is_suspended: bool` — 该 function_tag 是否被暂停（连续N次低于阈值）

> **术语统一规则**：verdict枚举值在JSON Schema和数据库中统一使用英文（passed/revise/low_confidence_passed/failed），中文仅在**前端展示**时映射（通过→passed，修改通过→revise，低置信度通过→low_confidence_passed，未通过→failed）。数据库contribution_memory表的referee_verdict列存储英文枚举值，确保数据流转编码一致。

**处理逻辑摘要**：
1. EMA更新 `accuracy`（见5.2节）
2. 计算 `rework_rate`（见5.3节）
3. 计算 `importance_score = 0.5×accuracy + 0.3×(1-rework_rate) + 0.2×count_normalized`（per-function-tag粒度）
4. 检查是否需要淘汰（连续N次低于阈值 → 标记 `is_suspended=1`，见5.5.1节）
5. 学生反馈微调 `importance_score`（±0.02，见5.7节）

> 本模块**只负责更新表现数据**，不生成内容、不调度、不评分。更新后的 `importance_score` 供**下一轮**调度使用（模块一）。

## 5.1 贡献记忆数据模型

### 5.1.1 SQLite表结构

> **修正说明**：原方案`agent_cards`表中`importance_score`为单一值，现为per-function-tag粒度，拆为`agent_cards`（静态信息）+`agent_performance`（动态表现）两张表。

```sql
-- Agent卡片表（静态信息）
CREATE TABLE agent_cards (
    agent_id TEXT PRIMARY KEY,
    agent_name TEXT NOT NULL,
    primary_function TEXT NOT NULL,
    secondary_functions TEXT NOT NULL,  -- JSON array
    domain_tags TEXT NOT NULL,  -- JSON array
    status TEXT DEFAULT "active",  -- active / eliminated
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Agent表现表（动态表现，per-function-tag粒度）
CREATE TABLE agent_performance (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    agent_id TEXT NOT NULL,
    function_tag TEXT NOT NULL,  -- 对应primary_function或secondary_functions中的某一项
    accuracy REAL DEFAULT 0.5,
    count INTEGER DEFAULT 0,
    rework_rate REAL DEFAULT 0.0,
    importance_score REAL DEFAULT 0.5,  -- 三因子加权：0.5×acc + 0.3×(1-rework) + 0.2×count_norm
    is_suspended BOOLEAN DEFAULT 0,  -- per-function-tag 暂停标记
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(agent_id, function_tag),
    FOREIGN KEY(agent_id) REFERENCES agent_cards(agent_id)
);

-- 贡献记忆表
CREATE TABLE contribution_memory (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    task_id TEXT NOT NULL,
    agent_id TEXT NOT NULL,
    function_tag TEXT NOT NULL,  -- 本次任务中该Agent以哪个功能标签参与
    task_type TEXT NOT NULL,  -- "单领域" / "跨领域" / "全链路" / "offline_eval"
    segment TEXT,  -- 该Agent负责的那一段（如"RAG架构段"）
    review_score REAL,  -- 审核团队段内评选得分
    importance_score REAL,  -- 本次任务计算出的importance_score（用于淘汰判定的历史查询）
    referee_verdict TEXT,  -- 英文枚举值："passed" / "revise" / "low_confidence_passed" / "failed"（前端展示时映射为中文）
    referee_modifications INTEGER DEFAULT 0,
    rework_type TEXT,  -- "none" / "minor" / "major"
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY(agent_id) REFERENCES agent_cards(agent_id)
);

-- 学生反馈表
CREATE TABLE student_feedback (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id TEXT NOT NULL,
    agent_id TEXT NOT NULL,
    function_tag TEXT NOT NULL,
    feedback_type TEXT NOT NULL,  -- 'helpful'|'not_helpful'|'content_error'|'difficulty_mismatch'
    comment TEXT,                 -- 学生具体反馈内容
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY(agent_id) REFERENCES agent_cards(agent_id)
);

-- 系统配置表（存储α值等全局参数）

## 5.2 EMA更新算法（详细）

```python
def update_accuracy(agent_id, function_tag, review_score):
    """
    更新某个Agent在某个function_tag下的accuracy
    EMA_SMOOTH: EMA衰减系数（常量0.8），旧数据权重=EMA_SMOOTH，新数据权重=1-EMA_SMOOTH
    EMA_SMOOTH越大，历史数据影响越大（越平滑）
    EMA_SMOOTH越小，新数据影响越大（越敏感）
    """
    row = query(
        "SELECT accuracy, count FROM agent_performance "
        "WHERE agent_id=? AND function_tag=?",
        (agent_id, function_tag)
    )
    old_accuracy = row["accuracy"]
    old_count = row["count"]
    
    new_accuracy = old_accuracy * EMA_SMOOTH + review_score * (1 - EMA_SMOOTH)
    new_count = old_count + 1
    
    execute(
        "UPDATE agent_performance SET accuracy=?, count=?, updated_at=? "
        "WHERE agent_id=? AND function_tag=?",
        (new_accuracy, new_count, now(), agent_id, function_tag)
    )
    return new_accuracy, new_count

# 示例：
# Agent_3在"RAG架构"上，历史accuracy=0.85，count=15
# 本次review_score=0.87
# 更新后：new_accuracy = 0.85*0.8 + 0.87*0.2 = 0.854, new_count=16
```

**EMA_SMOOTH选择依据**：
- `EMA_SMOOTH=0.8`：约最近5次数据占权重67%，既能反映近期表现，又不受单次异常影响
- 可在ablation实验中测试`EMA_SMOOTH=0.7`和`EMA_SMOOTH=0.9`的效果，选择最优

## 5.3 返工率计算

```python
def update_rework_rate(agent_id, function_tag, rework_score):
    """
    使用EMA平滑更新返工率（EMA_SMOOTH=0.8）
    
    输入：本次裁判判定的rework_score（0~1之间，分数越高=Agent输出质量越好）
    映射逻辑：rework_score越高 → 返工率越低（取反映射）
      - rework_score = 1.0 → 完全满意，mapped = 0.0（无返工）
      - rework_score = 0.0 → 完全不满意，mapped = 1.0（完全返工）
    
    新rework_rate = EMA_SMOOTH × 旧rework_rate + (1 - EMA_SMOOTH) × (1.0 - rework_score)
    """
    old_rate = query("SELECT rework_rate FROM agent_performance WHERE agent_id=? AND function_tag=?", (agent_id, function_tag))
    if old_rate is None:
        old_rate = 0.0
    
    # 取反映射：裁判高分=低返工率
    mapped_score = 1.0 - rework_score
    
    new_rate = EMA_SMOOTH * old_rate + (1 - EMA_SMOOTH) * mapped_score
    update("UPDATE agent_performance SET rework_rate=? WHERE agent_id=? AND function_tag=?", (new_rate, agent_id, function_tag))
    return new_rate
```

## 5.4 importance_score计算（per-function-tag粒度）

```python
def compute_importance_score(agent_id, function_tag):
    """
    综合权重计算，用于下次调度员遴选
    注意：importance_score是per-function-tag的，不是Agent级别的单一值
    """
    row = query(
        "SELECT accuracy, count, rework_rate FROM agent_performance "
        "WHERE agent_id=? AND function_tag=?",
        (agent_id, function_tag)
    )
    
    accuracy = row["accuracy"]
    rework_rate = row["rework_rate"]
    count = row["count"]
    
    # 冷启动保护：新Agent（count<5）使用默认值
    if count < 5:
        return 0.5  # 冷启动默认值
    
    # 三因子加权：准确率(0.5) + 返工率(0.3) + 调用频次(0.2)
    clamped_rework = min(rework_rate, 1.0)
    count_normalized = min(count / 100.0, 1.0)
    
    importance_score = 0.5 * accuracy + 0.3 * (1 - clamped_rework) + 0.2 * count_normalized
    importance_score = round(importance_score, 4)
    
    # 写回agent_performance表
    execute(
        "UPDATE agent_performance SET importance_score=? "
        "WHERE agent_id=? AND function_tag=?",
        (importance_score, agent_id, function_tag)
    )
    
    return importance_score
```

> **修正说明**：importance_score从Agent级单一值改为per-function-tag粒度。调度员选人时，根据学情画像中的`domain_hint`匹配到具体function_tag，然后查`agent_performance`表获取对应tag的importance_score。

## 5.5 动态淘汰机制（详细）

### 5.5.1 淘汰判定

```python
def check_elimination(agent_id):
    """
    检查某Agent是否应被淘汰。
    触发条件：某一function_tag下，连续3次 importance_score < 0.5
    
    注意：从contribution_memory表查询历史importance_score
    （agent_performance表因UNIQUE(agent_id, function_tag)约束每个组合仅1行，无法取历史序列）。
    
    遍历该Agent所有function_tag，逐个判定淘汰。
    """
    perfs = query(
        "SELECT function_tag, is_suspended FROM agent_performance WHERE agent_id=?",
        (agent_id,)
    )
    if not perfs:
        return
    
    threshold = 0.5  # 可配置，存储在system_config表
    
    for perf in perfs:
        if perf["is_suspended"]:
            continue  # 已挂起，跳过
        
        recent_scores = query(
            "SELECT importance_score FROM contribution_memory "
            "WHERE agent_id=? AND function_tag=? ORDER BY created_at DESC LIMIT 3",
            (agent_id, perf["function_tag"])
        )
        scores = [s["importance_score"] for s in recent_scores]
        
        # 连续3次低于阈值
        if len(scores) >= 3 and all(s < threshold for s in scores):
            # 标记该function_tag为suspended（per-function-tag粒度）
            execute(
                "UPDATE agent_performance SET is_suspended=1 "
                "WHERE agent_id=? AND function_tag=?",
                (agent_id, perf["function_tag"])
            )
            # 记录淘汰信息
            execute(
                "INSERT INTO elimination_log (agent_id, function_tag, reason) "
                "VALUES (?, ?, ?)",
                (agent_id, perf["function_tag"],
                 f"连续3次importance_score<{threshold}, function_tag={perf['function_tag']}")
            )
    
    # 淘汰后进入离线评估队列，积累20条新数据后重新评估
    # 目标淘汰率：5-10%（太高说明阈值太严，太低说明太松）
```

### 5.5.2 离线评估队列

```
被淘汰的Agent不直接丢弃，而是进入离线评估队列：

触发：Agent在某一function_tag下被suspended

离线评估流程：
  1. 该Agent在该function_tag下标记为is_suspended=1（agent_performance表）
  2. 后台定时任务：每周用10道标准测试题对该Agent评估
     （标准测试题来源：从7.2.2节100道测试用例中按该function_tag随机抽取10道，
      由人工标注的标准答案作为评判基准）
  3. 若连续2次评估accuracy > 0.7 → 解除suspended，恢复为active
  4. 若连续4次评估accuracy仍 < 0.5 → 永久淘汰（标记为"eliminated"）
  5. 评估结果写入contribution_memory表（task_type="offline_eval"）

意义：
  - 避免因少量异常数据误杀Agent
  - 给被淘汰Agent"翻盘"机会
  - 离线评估不占用在线服务资源
```

## 5.6 冷启动处理

### 5.6.1 新Agent加入时的默认值

```
问题：新加入的Agent，performance为空，importance_score = 三因子公式缺乏数据

解决方案：
  1. 新Agent加入时，在agent_performance表中为每个function_tag插入默认行：
     accuracy=0.5, count=0, rework_rate=0.0, importance_score=0.5
  2. 当count < 5时，强制使用默认值0.5，不计算（count_normalized不足以产生有意义的值）
  3. count >= 5时，切换到三因子公式正常计算
  4. 功能匹配度仍然生效（alpha=0.9时占90%权重），所以新Agent仍能凭功能标签被选到
```

### 5.6.2 人工预打标签规范

```
新Agent加入时，人工必须填写：
  1. primary_function（主功能，必填）
  2. secondary_functions（副功能，可选，但建议至少填1个）
  3. domain_tags（领域标签，必填，从限定枚举值中选择）

人工标签质量检查：
  - primary_function不应与其他Agent重复（重复意味着功能重叠，需合并或细化）
  - domain_tags至少1个，最多3个
```

注意：学生反馈权重低于审核团队和裁判团的评分，仅作微调（±0.02），

```

# 第六部分：编排器与知识库方案

## 6.1 编排器设计（FSM状态机）

> 对齐赛题要求：系统需有明确的"分析→生成→校验→决策"协同闭环流程。编排器是实现这一闭环的引擎。

### 6.1.1 FSM状态定义

```
状态机：IDLE → PROFILING → DISPATCHING → GENERATING → REVIEWING → FOCUSING → JUDGING → FORMATTING → COMPLETE

各状态说明：

[IDLE]
  触发：学生提交问题
  动作：创建task_id，进入PROFILING
  LLM调用：0次

[PROFILING]
  触发：从IDLE进入
  动作：学情画像生成器生成/增量更新学情画像
  LLM调用：1次（学情画像生成）
  出口：画像JSON生成完毕 → DISPATCHING

[DISPATCHING]
  触发：画像生成完毕
  动作：调度员根据标签匹配+importance_score遴选候选Agent（每段2个）
  LLM调用：0次（纯SQL查询+计算）
  出口：候选列表确定 → GENERATING

[GENERATING]
  触发：候选列表确定
  动作：各段候选Agent并行输出
  LLM调用：每段2次（并行），总次数=段数×2
  出口：所有候选输出完毕 → REVIEWING

[REVIEWING]
  触发：候选输出完毕
  动作：审核团队3人并行评分 → 段内评选 → 跨段一致性审查（多段场景）
  LLM调用：3次（3人并行评分）；多段场景各段独立
  出口：各段最优确定 → FOCUSING

[FOCUSING]
  触发：各段最优确定
  动作：最优Agent聚焦输出（确认+完善+Schema约束）
  LLM调用：每段1次
  出口：聚焦输出完毕 → JUDGING

[JUDGING]
  触发：聚焦输出完毕
  动作：裁判团3人并行审查 → 汇总 → 分歧解决（如有2:1分歧）+ 候选Agent辩论（与分歧解决并行）
  LLM调用：3次（3人并行审查）；分歧解决+候选辩论可能+1-2次（仅~30%场景）
  出口：裁判裁定 → FORMATTING 或 REVISING（退回修改聚焦输出后重审，最多2次）

[FORMATTING]
  触发：裁判团通过
  动作：资源生成Agent按条件生成3种形态
  LLM调用：1-3次（讲义必选1次，实操指南和测试题条件触发各1次）
  出口：资源生成完毕 → COMPLETE

[COMPLETE]
  触发：资源生成完毕
  动作：写贡献记忆，更新表现标签，推送结果给学生
  LLM调用：0次

异常状态：
[REVISING] → Agent修改FocusedOutput后回到JUDGING重审（修改次数+1，上限2次）
[ERROR] → 任何阶段出错，记录日志，返回学生友好错误信息

延伸路径状态（从COMPLETE触发，可选而非必经）：
[QUIZ_EVAL] → 学生答题验证，计算正确率，判定迭代方向
  触发：前端/quiz_submit接口收到答题结果，或/feedback接口收到难度/内容反馈
  动作：计算正确率，判定方向（正确率<60%→REDIMENSION，≥85%→ADVANCE，"内容有误"→RECHECK）
  LLM调用：0次（纯计算）

[REDIMENSION] → 降维解释，资源生成Agent用降维Prompt重新生成同一知识点
  LLM调用：1-3次（降维讲义1次+降维实操/测试题各条件触发1次）
  出口：降维资源交付 → HEURISTIC_FOLLOWUP

[ADVANCE] → 进阶挑战，追加1道动态进阶题
  LLM调用：1次（生成1道进阶题）
  出口：进阶题交付 → HEURISTIC_FOLLOWUP

[RECHECK] → 审核复检，审核团队对被质疑内容进行专项复检
  LLM调用：1-3次（审核员复检）
  出口：复检通过→回复学生；发现错误→进入REDIMENSION修正

[HEURISTIC_FOLLOWUP] → 启发式追问导学，学情诊断Agent基于上下文动态生成1-2个追问问题
  LLM调用：1次
  出口：追问交付 → 学生回答可触发新一轮PROFILING（画像增量更新），形成完整闭环

### 6.1.3 交付后延伸路径（动态迭代闭环）

> 对齐赛题要求：*"提供基于学习交互反馈的动态迭代机制（如根据答题正确率，多智能体协同决策是否对知识点进行'降维解释'或生成'进阶挑战任务')"* 及评分标准 *"动态决策更新"* 环节。

主FSM在FORMATTING→COMPLETE后结束，但系统提供**触发式延伸路径**——学生可选择进入验证闭环，实现"交付→验证→调整→追问"的动态迭代。这不是必经状态，而是学生主动触发或系统自动推荐的**可选分支**。

```
延伸路径（从COMPLETE触发）：

触发条件（任一满足即进入）：
  ① 学生答题验证：分阶测试题的第3题及以上（进阶挑战）完成后，学生提交答案
  ② 学生反馈"难度不匹配"：点击反馈按钮选择"难度不匹配"
  ③ 学生反馈"内容有误"：点击反馈按钮选择"内容有误"
  ④ 系统自动推荐：知识盲区热力图检测到新盲区，推荐追问

延伸状态机：

[QUIZ_EVAL]（答题验证）
  输入：学生答题结果（正确率 + 各题详情）
  动作：计算正确率，判定迭代方向
  规则：
    - 正确率<60% → 进入[REDIMENSION]（降维解释）
    - 正确率≥60%且<85% → 进入[REDIMENSION]（轻度降维）
    - 正确率≥85% → 进入[ADVANCE]（进阶挑战）
  LLM调用：0次（纯计算）

[REDIMENSION]（降维解释）
  输入：原FocusedOutput + 学生画像 + 答题正确率
  动作：资源生成Agent用降维Prompt重新生成同一知识点
  降维策略：
    - 入门水平降维：加生活类比、删专业术语、拆5步→8小步、加"为什么这样？"引导
    - 中级水平降维：加过渡概念解释、补"前置知识回顾"段落
    - 进阶水平降维：拆复杂推理链为子步骤、加中间验证节点
  LLM调用：1-3次（降维讲义1次 + 降维实操/测试题各条件触发1次）
  出口：降维资源交付 → [HEURISTIC_FOLLOWUP]

[ADVANCE]（进阶挑战）
  输入：原FocusedOutput + 学生画像 + 答题正确率
  动作：从3题扩展到4题，追加1道动态进阶题（跨知识点综合或边界条件挑战）
  进阶策略：
    - 题目难度提升：从"应用"级升至"分析/设计"级
    - 跨知识点联动：将当前知识点与相邻知识点组合出题
    - 开放性增加：减少选择题，增加需要自主推理的题目
  LLM调用：1次（生成1道进阶题）
  出口：进阶题交付 → [HEURISTIC_FOLLOWUP]

[RECHECK]（审核复检）
  输入：学生反馈"内容有误" + 原输出
  动作：审核团队对被质疑内容进行专项复检
  LLM调用：1-3次（审核员复检）
  出口：复检通过→回复学生"经复检确认正确"；复检发现错误→进入[REDIMENSION]修正

[HEURISTIC_FOLLOWUP]（启发式追问导学）
  输入：刚交付的资源内容 + 学生画像 + 知识盲区热力图
  动作：学情诊断Agent基于上下文动态生成1-2个追问问题，引导学生深入思考
  追问生成规则：
    - 追问内容与刚交付资源的核心知识点相关
    - 追问形式：不是判断题（"懂了吗？"），而是引导题（"你能试着解释XX和YY的关系吗？"/"如果将参数A从0.1改为0.5，你觉得结果会怎样变化？"）
    - 追问难度略高于资源难度，但不超出学生画像范围
    - 追问不是固定话术，而是LLM根据当前上下文实时生成（区别于navigation路径的固定追问模板）
  LLM调用：1次
  出口：追问交付 → 学生回答可触发新一轮PROFILING（画像增量更新），形成完整闭环
```

> **延伸路径与主FSM的关系**：主FSM保证基础交付（分析→生成→校验→决策→交付），延伸路径在交付后提供可选的深度迭代。两者共用相同的Agent和Schema体系，不需要新增Agent角色，只需要在编排器中增加触发式状态转移逻辑。

**实时状态推送（ws_manager.push_state）**：

系统内置WebSocket状态推送机制，每个FSM阶段切换时将当前状态、产物摘要、进度信息推送到前端。

```python

**推送内容时序表**：

| FSM阶段 | 初始推送 | 完成推送 |
|---------|---------|---------|
| IDLE | 状态切换 | — |
| PROFILING | 状态名称 | 学情画像JSON（完整） |
| DISPATCHING | 状态名称 | intent类型 + 段数 |
| GENERATING | 状态名称 | 已生成段数 |
| REVIEWING | 状态名称 | 获胜Agent列表 |
| FOCUSING | 状态名称 | 聚焦输出段数 |
| JUDGING | 状态名称 | 裁决结果 + 段数 |
| FORMATTING | 状态名称 | 各形态是否生成 |
| COMPLETE | 状态名称 | revision次数 + session_id |

**状态缓存更新**：每阶段完成后更新预计算字段（revision_count、session_id），保证`/api/status`接口返回最新状态，避免前端轮询延迟。

```
技术选型：FastAPI + 异步任务编排

核心代码结构（伪代码）：

class Orchestrator:
    def __init__(self):
        self.state_machine = FSM()
        self.db = SQLiteClient()
        self.knowledge_base = ChromaClient()
    
    async def process_question(self, question, session_id):
        task_id = generate_task_id()
        state = "PROFILING"
        
        while state != "COMPLETE":
            if state == "PROFILING":
                profile = await self.profile_generator.generate(question, session_id)
                state = "DISPATCHING"
            
            elif state == "DISPATCHING":
                candidates = self.dispatcher.dispatch(profile)
                state = "GENERATING"
            
            elif state == "GENERATING":
                outputs = await asyncio.gather(*[
                    agent.generate(question, profile) 
                    for agent in candidates
                ])
                state = "REVIEWING"
            
            elif state == "REVIEWING":
                review_results = await asyncio.gather(*[
                    self.verifier.review(outputs),
                    self.skeptic.review(outputs),
                    self.evaluator.review(outputs)
                ])
                best_agents = self.select_best(review_results, outputs)
                # 跨段一致性审查（仅多段场景触发）
                if self.is_multi_segment:
                    consistency_issues = self.check_cross_segment_consistency(
                        self.segment_best_outputs
                    )
                    if consistency_issues:
                        # 局部修复：指定相关Agent做小改，不回GENERATING全量重跑
                        # 修改范围判定见4.3.3节：小改不需再过裁判团，大改需再过裁判团
                        self.fix_consistency_issues(consistency_issues)
                    state = "FOCUSING"
                else:
                    state = "FOCUSING"
            
            elif state == "FOCUSING":
                focused = await asyncio.gather(*[
                    agent.focused_output(question, profile) 
                    for agent in best_agents
                ])
                state = "JUDGING"
            
            elif state == "JUDGING":
                verdicts = await asyncio.gather(*[
                    judge.judge(focused, profile) 
                    for judge in self.referees
                ])
                result = self.resolve_judgment(verdicts)
                if result["passed"]:
                    state = "FORMATTING"
                elif result["revise"] and result["revision_count"] < 2:
                    result["revision_count"] += 1  # 修改次数递增，上限2次
                    state = "REVISING"  # 进入修改状态，Agent根据裁判反馈修改后重审
                else:
                    state = "FORMATTING"  # 低置信度强制通过
            
            elif state == "REVISING":
                # Agent根据裁判团反馈修改FocusedOutput
                await self.best_agent.revise(focused, result["issues"])
                state = "JUDGING"  # 修改完成后回到裁判团重审
            
            elif state == "FORMATTING":
                # 资源生成Agent按条件触发3种形态
                lecture = await self.resource_agent.generate_lecture(focused, profile)  # 讲义（必选，1次调用）
                practice_guide = None
                quiz = None
                if focused.get("code_example"):  # 实操指南条件触发
                    practice_guide = await self.resource_agent.generate_practice(focused, profile)  # +1次调用
                if profile["question_type"] in ["概念理解", "操作步骤", "架构设计"]:  # 测试题条件触发
                    quiz = await self.resource_agent.generate_quiz(focused, profile)  # +1次调用
                resources = {"lecture": lecture, "practice_guide": practice_guide, "quiz": quiz}
                state = "COMPLETE"
        
        # 写贡献记忆
        self.write_contribution_memory(task_id, ...)
        return resources
    
    # ─── 延伸路径（从COMPLETE触发，异步事件驱动）───
    async def handle_extension(self, task_id, event_type, event_data):
        """
        延伸路径在主FSM完成后，由学生反馈/答题提交等异步事件触发。
        不是主FSM的一部分，而是可选的延伸闭环。
        event_type: "quiz_submit" / "feedback_difficulty" / "feedback_error" / "system_recommend"
        """
        state = "QUIZ_EVAL"
        
        if event_type == "quiz_submit":
            # 计算答题正确率
            accuracy = self.calculate_quiz_accuracy(event_data)
            if accuracy < 0.60:
                state = "REDIMENSION"  # 降维解释
            elif accuracy >= 0.85:
                state = "ADVANCE"      # 进阶挑战
            else:
                state = "REDIMENSION"  # 轻度降维（正确率60%-85%）
        
        elif event_type == "feedback_difficulty":
            state = "REDIMENSION"  # 学生反馈难度不匹配→降维
        
        elif event_type == "feedback_error":
            state = "RECHECK"  # 学生反馈内容有误→审核复检
        
        elif event_type == "system_recommend":
            state = "HEURISTIC_FOLLOWUP"  # 系统推荐追问
        
        if state == "QUIZ_EVAL":
            # 已在上面判定方向，跳过
            pass
        
        elif state == "REDIMENSION":
            profile = self.get_profile(task_id)
            focused = self.get_focused_output(task_id)
            resources = await self.resource_agent.generate_dimension_reduction(focused, profile, event_data)
            state = "HEURISTIC_FOLLOWUP"
        
        elif state == "ADVANCE":
            focused = self.get_focused_output(task_id)
            profile = self.get_profile(task_id)
            advance_question = await self.resource_agent.generate_advance_challenge(focused, profile)
            state = "HEURISTIC_FOLLOWUP"
        
        elif state == "RECHECK":
            focused = self.get_focused_output(task_id)
            review_result = await self.review_team.recheck(focused, event_data)
            if review_result["has_error"]:
                state = "REDIMENSION"  # 复检发现错误→进入降维修正
            else:
                return {"response": "经复检确认内容正确", "followup": None}
        
        # 启发式追问导学
        if state == "HEURISTIC_FOLLOWUP":
            profile = self.get_profile(task_id)
            recent_content = self.get_recent_resources(task_id)
            followup_questions = await self.profile_generator.generate_heuristic_followup(
                recent_content, profile
            )
            return {"followup_questions": followup_questions}
        
        return None
```

## 6.2 SOP中间产物链定义（MetaGPT真正落地）

> **设计依据**：MetaGPT论文核心发现——结构化文档替代自然语言聊天能显著提升多Agent协作质量（Pass@1提升4.2-5.4%）。当前方案只定义了FocusedOutput一个Schema，其他中间产物（候选输出、审核反馈、裁判裁决）散落各处无统一规范。定义完整SOP链后，每个阶段的输入输出都是确定性的，调试和迭代都有据可查。

### 6.2.1 完整SOP中间产物链

```
Stage 1 → StudentProfile JSON     （学情画像，模块一输出）
Stage 2 → CandidateOutput JSON    （候选输出+自评估，模块二输出，已定义于3.4.4节）
Stage 3 → ReviewFeedback JSON     （审核反馈，模块三输出）← 新增Schema
Stage 4 → FocusedOutput JSON      （聚焦输出，模块二输出，已定义于3.5节）
Stage 5 → JudgeVerdict JSON       （裁判裁决，模块三输出）← 新增Schema
Stage 6 → ResourcePackage JSON    （资源包，模块二输出）

继承关系（发布-订阅模式）：
  StudentProfile → 被 Stage 2/3/4/5/6 订阅（所有下游都需要学情信息）
  CandidateOutput → 被 Stage 3 订阅（审核团队基于候选输出评分）
  ReviewFeedback → 被 Stage 4 订阅（聚焦输出基于审核反馈改进）← 改进2的载体
  FocusedOutput → 被 Stage 5 订阅（裁判团基于聚焦输出审查）
  JudgeVerdict → 被 Stage 6 订阅（资源生成基于裁决结果生成）
```

## 6.4 跨语言检索方案（中文问题→英文文档）

### 6.4.1 问题

知识库来源多为英文文档，学生问题为中文，直接跨语言语义检索准确率较低。

### 6.4.2 解决方案：**多语言Embedding模型**

```
推荐方案：使用BAAI/bge-m3模型

选型理由：
  - bge-m3是bge-large-zh-v1.5的升级版，支持多语言（中/英/日/韩等100+语言）
  - 同一模型同时支持稠密检索、稀疏检索、多向量检索三种模式
  - 跨语言检索能力显著优于bge-large-zh-v1.5（MTEB跨语言榜单Top3）
  - 本地运行，无API成本，模型大小约2.2GB

使用方式：
  1. 知识库文档切分后，用bge-m3编码，存入向量库
  2. 学生问题（中文）直接用同一模型编码，检索
  3. 支持混合检索（稠密+稀疏），提升召回率

备选方案：text-embedding-ada-002（OpenAI，双语均强，但需API调用）
```

## 6.5 切分与入库流程

```python
# 详细流程（一次性预处理脚本）

# Step 1: 获取原始文档
docs = load_documents()  # 从Markdown/PDF/网页加载

# Step 2: 按章节切分（保留结构信息）
from langchain.text_splitter import MarkdownHeaderTextSplitter
headers_to_split_on = [
    ("#", "title"),
    ("##", "section"),
    ("###", "sub_section")
]
splitter = MarkdownHeaderTextSplitter(headers_to_split_on)
chunks = splitter.split_text(docs)

# Step 3: 每个chunk补充元数据
for chunk in chunks:
    chunk.metadata["source_doc"] = doc_name
    chunk.metadata["section_path"] = chunk.metadata["title"] + " > " + chunk.metadata.get("section", "")
    chunk.metadata["applicable_agents"] = match_agents(doc_name)

# Step 4: Embedding + 入库（使用bge-m3）
from FlagEmbedding import BGEM3FlagModel
model = BGEM3FlagModel("BAAI/bge-m3", use_fp16=True)

embeddings = model.encode([c.page_content for c in chunks])
collection.add(
    documents=[c.page_content for c in chunks],
    embeddings=embeddings.tolist(),
    metadatas=[c.metadata for c in chunks],
    ids=[f"chunk_{i}" for i in range(len(chunks))]
)
```

## 6.6 检索策略

```
检索触发时机：
  1. Verifier事实核查时：对聚焦输出JSON中的每个knowledge_refs条目，去向量库验证
  2. 裁判团溯源标注时：对最终通过的输出，逐条标注知识库来源
  3. Agent输出时（可选，RAG增强）：Agent在输出前先检索相关知识库片段，融入答案

检索参数：
  - Top-K：验证时K=3（取Top-3相关片段做核对）
  - Score阈值：相似度<0.6的检索结果视为"无法确认"
  - bge-m3混合检索：默认启用稠密+稀疏混合模式，提升跨语言召回率

分类过滤（filter_agent）：
  知识库chunk入库时标注所属Agent_name（即该chunk最相关的领域Agent名称）。
  检索时，Agent按自己的agent_name过滤chunk：
    filter_agent = agent.agent_name（如"LangChain组件Agent"只检索与其相关的chunk）
  作用：每个Agent只检索自己分类下的chunk，提高检索精度，避免跨领域噪声。
  若filter_agent过滤后无结果 → fallback到全局无过滤检索，确保知识库可访问性。
```

## 8.4 响应时间优化方案

### 8.4.1 各场景API调用量及响应时间估算

> **基准假设**：每次LLM API调用实际耗时2-5秒（按3秒均值估算）。并行调用受API速率上限限制，但同一场景内的独立调用可并发执行。

**统一模式**：

| 场景 | 总调用次数 | 并行策略 | 串行关键路径 | **预计响应时间** |
|------|----------|---------|------------|---------------|
| 单领域 | 9次 | 2候选并行 | 画像→候选×2并行→3审核→聚焦→3裁判 | **≤20秒** |
| 跨领域（2段） | 19次 | 每段候选并行 | 画像→4候选→2×(3审核)→2聚焦→2×(3裁判)+跨段审查 | **≤27秒** |
| 全链路（4段） | 37次 | 段间候选并行 | 画像→8候选→4×(3审核)→4聚焦→4×(3裁判)+跨段审查 | **≤38秒** |
| 超7领域 | 分阶段 | 先回答前3领域 | 同3领域估算 | **≤33s/批次** |

> **演示说明**：挑战杯现场演示预计单领域场景约20秒，跨领域约27秒。现场可提前录制演示视频作为备份。
>
> **退回修改代价**：裁判团退回修改需额外 聚焦Agent修改(1次) + 裁判团重审(3次) = +8~10秒。按返工率20%估算，加权响应时间 ≈ 20×0.8 + 28×0.2 ≈ 22秒（单领域）。
>
> **候选辩论代价**：裁判团2:1分歧时触发候选Agent辩论，额外+1-2次调用（约+3-6秒）。按30%分歧率估算，加权额外时间 ≈ 3×0.3 ≈ 1秒，已含在上述估算的容差范围内。

### 8.4.2 优化方案

```
优化1：并行化（已实现）
  - 审核团队3人调用并行（节省2×3秒）
  - 裁判团3人调用并行（节省2×3秒）
  - 多段候选输出并行调用（节省N×3秒）

优化2：缓存学情画像（针对连续对话）
  - 同一学生的后续问题，不重新生成学情画像（节省3秒）
  - 学情画像在session内持久化，增量更新而非全量重建

优化3：候选输出提前截断（针对超长输出）
  - 设置max_tokens=512，防止Agent输出过长
  - 聚焦输出阶段才允许完整输出（max_tokens=2048）

优化4：裁判团快速通道（针对高置信度场景）
  - 若审核评分全票一致（分差<0.05），裁判团只做溯源标注，不做分歧解决
  - 预计节省3-6秒

优化5：条件触发资源生成
  - 讲义必选（1次调用）
  - 实操指南和测试题按条件触发，避免不必要的调用

优化目标：
  - 单领域：≤20秒
  - 跨领域（2段）：≤27秒
  - 全链路（4段）：≤38秒
```

> **前提说明**：以上响应时间估算基于API不限速、并行优化条件下。实际qwen-max单次生成约3-8秒（取决于输出长度），若API限速或排队，响应时间可能增加30-50%。建议生产环境部署本地模型（如DeepSeek-V3）以消除速率限制。

## 8.5 成本控制机制（分层模型策略）

> **设计依据**：DyLAN论文另一发现——不是所有Agent都需要最强模型，弱模型在特定任务上足够。当前方案所有阶段都用同一LLM，成本高昂。分层策略让"高质量模型用在最关键环节"成为设计原则。

### 8.5.1 分层模型配置

| 阶段 | 模型等级 | 推荐模型 | 单次成本 | 理由 |
|------|---------|---------|---------|------|
| 学情画像生成 | 中档 | DeepSeek-V3 | ~$0.01 | 结构化分类任务，不需要顶级推理 |
| 候选Agent输出 | 中档 | DeepSeek-V3 | ~$0.01 | 需要领域知识但不需要顶级推理 |
| 候选自评估（self_confidence） | — | 随候选输出同轮返回 | $0 | DyLAN设计：置信度与输出同轮生成，0额外调用 |
| 审核团队评分 | 中档 | DeepSeek-V3 | ~$0.01 | 需要理解内容但评分维度固定 |
| 聚焦输出（含反思） | 高档 | qwen-max | ~$0.05 | 最终质量决定环节，需要顶级推理+反思改进 |
| 裁判团裁决 | 高档 | qwen-max | ~$0.05 | 事实核查和逻辑审查需要顶级能力 |
| 候选Agent辩论 | 中档 | DeepSeek-V3 | ~$0.01 | 证据提交，不需要顶级推理（仅2:1分歧时触发） |
| 资源生成 | 中档 | DeepSeek-V3 | ~$0.01 | 格式化转换，不需要顶级推理 |

> **模型选型说明**：高档统一采用通义千问 `qwen-max`（dashscope，OpenAI-compatible 接口），中档采用 `deepseek-chat`（DeepSeek-V3），低档采用 `qwen-turbo` 做轻量判断。该混合档在中文推理质量与成本上优于全 GPT-4o 方案，且三者均为 OpenAI-compatible，可无缝切换；若 qwen-max 不可用，聚焦/裁判环节降级为 deepseek-chat 并增派 1 名裁判。

### 8.5.2 成本估算

```
单领域成本估算（分层模型）：
  画像1×$0.01 + 候选2×$0.01 + 自评估0 + 审核3×$0.01 
  + 聚焦1×$0.05 + 裁判3×$0.05 + 资源1×$0.01
  = $0.01 + $0.02 + $0.03 + $0.05 + $0.15 + $0.01
  = $0.27/次问答

> 注：$0.01/call为DeepSeek-V3调用的均值估算（输入$0.27/M tokens + 输出$1.10/M tokens，典型单次500-1500 output tokens），实际随输出长度浮动。聚焦输出和裁判审查的输出更长（含完整JSON Schema），实际成本可能高于$0.05/call。

对比全高档模型(qwen-max)方案：
  9×$0.05-0.15 = $0.45-1.35/次问答

降本幅度：40-80%

100名学生试点项目（每人平均20次提问）：
  分层模型：100×20×$0.27 = $540
  全高档模型(qwen-max)：100×20×$0.45-1.35 = $900-2,700
  节省：$360-2,160
```

### 8.5.3 模型降级策略（含全链路过程降级）

```
若高档模型（qwen-max）不可用：
  1. 聚焦输出 → 降级为DeepSeek-V3 + 增加审核严格度
  2. 裁判团 → 降级为DeepSeek-V3 + 增加1名裁判（4人表决）

若中档模型（DeepSeek-V3）不可用：
  1. 所有中档阶段 → 降级为qwen-turbo（成本略增但可用性保证）
  2. 候选输出max_tokens限制为512（防止低成本模型冗长输出）

本地部署方案（完全离线）：
  全部使用DeepSeek-V3本地部署，成本$0（需1×A100 GPU）
  代价：响应时间增加约50%（本地推理速度低于API）
```

#### 全链路过程降级（代码实现级）

除模型降级外，系统在FSM各阶段均实现细粒度降级策略，确保单个阶段失败不中断主流程：

| FSM阶段 | 降级策略 | 实现位置 |
|---------|---------|---------|
| PROFILING | LLM调用失败→使用默认画像（ENTRY/理科无编程/快速上手），不中断主流程 | orchestrator._do_profiling() |
| DISPATCHING | 画像为空→使用默认IntentType.GENERATION，全部候选出击 | orchestrator._do_dispatching() |
| GENERATING | 候选Agent调用失败→跳过该候选，使用成功候选的输出 | orchestrator._do_generating() |
| FOCUSING | 聚焦输出调用失败→用候选输出直接构造最小FocusedOutput（conclusion≈候选输出，reasoning_steps补充至3步） | orchestrator._do_focusing() |
| REVIEWING | 审核团队全部调用失败→跳过审核，候选输出直接进入聚焦（前端显示黄色警告'未经多角度审核'） | orchestrator._do_reviewing() |
| JUDGING | 裁判团全部调用失败→跳过裁判，直接输出聚焦结果+标注'未经裁判团审查' | orchestrator._do_judging() |
| FORMATTING | 资源生成失败→仅生成讲义（Lecture降级模式），实操指南和测试题为null | orchestrator._do_formatting() |
| KNOWLEDGE_BASE | 知识库不可用→跳过RAG增强，标记low_confidence_segments，审核团队自然给出低分 | orchestrator._do_generating()中双低分支 |

**设计原则**：
1. 主流程永不中断：任何阶段失败都使用前序产物或默认值继续
2. 前端/日志透传降级状态：每个降级事件记录到日志，前端显示对应标注（黄色警告/灰色标注）
3. 降级不逆转：一旦降级，后续阶段不能自动升级（需人工介入或下一轮重新尝试）

# 第十一部分：创新点与评分标准映射

## 11.1 五大创新点（逐条对齐赛题评分标准）

### 创新点1：两层辩论机制——候选Agent辩论+裁判团分歧解决（对应赛题"辩论机制"）

**赛题原文**：*"引入'辩论与交叉验证'机制以消除大模型在专业领域的'幻觉'"*

**本方案创新**：
- **候选Agent辩论**（Debate论文核心落地）：裁判团2:1分歧时，落选候选Agent可质疑获胜方输出，获胜方必须辩护——让真正懂领域的内容生产者参与辩论，而非仅靠裁判（外行审查内行）判断
- **裁判团分歧解决**：合并原DEBATING/PROTECTING死路径为统一的DISSENT_RESOLVE——少数方举证→多数方回应→僵持时裁判长裁决
- **MaW→C转化路径**：落选候选可能看到获胜者没看到的问题，用证据说服多数方（Debate论文发现：MaW→C转化对准确率贡献最大）
- 自信度隐藏：裁判互不可见自信度，消除锚定效应（Debate论文：自信度可见性对准确率不显著，p>0.05）

**技术创新性评分指向**：解决"幻觉"问题的方案具备突破性。

### 创新点2：三重交叉验证+反馈回流架构（对应赛题"交叉验证"与"协同闭环"）

**赛题原文**：*"多智能体间的创新协同架构（如引入'辩论与交叉验证'机制）"*

**本方案创新**：
- 第一重：审核团队3人独立评分（不同锚定物）
- 第二重：裁判团3人独立裁决 + 候选Agent辩论（内容生产者层面交叉验证）
- 第三重：贡献记忆闭环反馈（历史表现数据参与决策）
- **审核反馈回流**（MAR论文核心落地）：审核团队的具体问题传给获胜Agent做反思改进，而非仅用于选最优——闭环中有反馈回流，不是单向流水线

三层验证环环相扣，任一环节均可拦截错误，**幻觉率目标≤3%**（赛题要求<5%）。

### 创新点3：完整SOP中间产物链+高保真溯源（对应赛题"高保真知识溯源与约束生成"）

**赛题原文**：*"实现高保真知识溯源与约束生成"*

**本方案创新**：
- **完整6个SOP中间产物Schema**（MetaGPT论文核心落地）：StudentProfile→CandidateOutput→ReviewFeedback→FocusedOutput→JudgeVerdict→ResourcePackage，发布-订阅模式
- 裁判团逐条标注知识库来源（`knowledge_refs`字段，含来源文档+章节+验证状态）
- 聚焦输出强制Schema约束（MetaGPT发现：结构化输出Pass@1提升4.2-5.4%）
- 溯源是生成时强制（SOP链中每步都有结构化溯源字段），不是裁判事后补标注

### 创新点4：动态贡献记忆+候选自评估驱动的选人优化（对应DyLAN论文）

**赛题评分标准**：*"核心技术方案具备突破性与可行性"*

**本方案创新**：
- **候选自评估self_confidence**（DyLAN论文核心落地）：Agent输出时附带对当前问题的信心分——历史分（importance_score）+ 当下分（self_confidence）= DyLAN完整动态选择
- 双低触发RAG：两个候选self_confidence都<0.5时自动触发知识库增强
- `importance_score(function_tag) = 0.5×accuracy + 0.3×(1-rework_rate) + 0.2×count_normalized`，per-function-tag粒度
- α动态切换：冷启动靠人工标签，数据积累后自动切换到表现标签
- 离线评估队列：被淘汰Agent有"翻盘"机会，避免误杀
- **选人准确率随系统运行时间持续提升**（闭环优化的核心体现）

**补充——反向怀疑（Debate论文"强模型悖论"落地）**：
- 反向怀疑（被动触发）：基于输出内容特征自动触发严格审查，不依赖外部评分
- 触发条件：信息密度高（refs≥5）/ 代码复杂（行数≥20）/ 推理链长（steps≥8）
- **同一套裁判机制，对高质量输出自动更严，对低质量输出适度宽松**，真正实现"辩证审查"而非"一刀切"

> **候选辩论归入创新点1**：候选Agent辩论机制已在创新点1详细论述，此处不重复。创新点4的独特贡献是"反向怀疑"机制——被动触发式严格审查。两者互补：候选辩论是"主动质疑"，反向怀疑是"被动触发"，共同构成辩论机制的完整闭环。

### 创新点5：启发式追问+动态迭代闭环（对应赛题"动态追问与启发式交互导学"）

**赛题原文**：*"探索大模型驱动下的动态追问与启发式交互导学技术，打破静态资源的单向输入局限"*

**本方案创新**：
- **启发式追问**（交付后延伸路径的HEURISTIC_FOLLOWUP状态）：资源交付后，学情诊断Agent基于刚交付内容的topic + 学生画像 + 知识盲区热力图，动态生成1-2个追问问题引导学生深入思考——不是固定话术（如"你想学哪个阶段？"），而是LLM根据当前上下文实时生成的引导性问题
  - 例："你能试着解释RAG的检索阶段和生成阶段是怎么配合的吗？"（引导学生主动构建知识关联）
  - 例："如果把top_k参数从5改为20，检索结果会有什么变化？为什么？"（引导推理而非给出答案）
- **动态迭代闭环**（交付后延伸路径）：学生答题/反馈后，系统进入验证→调整闭环——低正确率触发降维解释、高正确率触发进阶挑战、反馈"内容有误"触发审核复检——不是"交付即结束"，而是"交付→验证→调整→追问"的触发式深度迭代
- 两者形成闭环：追问引导学生参与验证 → 验证结果驱动调整 → 调整后追问引导学生反思 → 循环持续直到学生掌握
- **打破了静态资源的单向输入局限**——资源不是"交付→结束"，而是"交付→互动→调整→追问→再交付"的持续对话

【输出格式（严格JSON）】
{
  "verdict": "passed / revise / low_confidence_passed / failed",
  "confidence": "高 / 中 / 低",
  "issues": ["具体问题描述（若通过则为空数组）"],
  "verification_coverage": 0.0-1.0,
  "retrieved_sources": ["知识库来源列表"]
}

只输出JSON。
```

## 附录C：API调用量分场景详细估算

| 场景 | 步骤 | LLM调用次数 | 可并行组 | 响应时间 |
|------|------|------------|---------|----------|
| 单领域（1段） | 候选(2)+审核(3)+聚焦(1)+裁判(3) | **9次** | 候选×2并行；审核×3并行；裁判×3并行 | **~20s** |
| 跨领域（2段） | 候选(4)+审核(6)+跨段审查(1)+聚焦(2)+裁判(6) | **19次** | 各段候选并行；段内审核/裁判并行 | **~27s** |
| 全链路（4段） | 候选(8)+审核(12)+跨段审查(1)+聚焦(4)+裁判(12) | **37次** | 高度并行化 | **~38s** |

**注意**：
- 以上为核心管线（FOCUSING→FORMATTING→COMPLETE）调用次数，不含学情诊断（+1）和资源生成（+1~3，条件触发），两者为边缘LLM调用，不纳入管线核心统计。
- 各段审核/裁判可分段并行执行，实际耗时并非简单相加。
- 若裁判团退回修改，追加~8秒（聚焦Agent修改+裁判团重审）。
- 候选Agent辩论：当裁判团出现2:1分歧时（约30%场景），触发候选辩论额外+1-2次调用，加权后平均额外≈0.3-0.6次，已含在容差范围内。

## 附录D：参考文献

1. **DyLAN: Dynamic LLM Agent Network** (EMNLP 2024)  
   - 核心发现：Agent Importance Score无监督动态打分；动态淘汰+早停机制；Agent应根据当前任务动态评估自身相关性  
   - 在本方案中的应用：Agent池动态贡献分（2.4）；动态淘汰+离线评估（5.5）；**候选自评估self_confidence**（3.4.4）——历史分+当下分=DyLAN完整动态选择

2. **Can LLM Agents Really Debate?** (EMNLP 2024)  
   - 核心发现：多数压力抑制独立纠正（弱模型仅3.6%）；MaW→C转化贡献最大；自信度可见性不显著（p>0.05）；强模型悖论  
   - 在本方案中的应用：分歧解决DISSENT_RESOLVE（4.4.2）；**候选Agent辩论**（4.4.2）——落选候选质疑+获胜候选辩护，MaW→C转化路径真正落地；基于内容特征的反向怀疑（4.4.3）；隐藏自信度

3. **MAR: Multi-Agent Reflexion Improves Reasoning Abilities in LLMs** (ICLR 2025)  
   - 核心发现：单Agent反思存在确认偏误；Persona多样性（Verifier/Skeptic/Logician/Creative）；反思后改进Pass@1提升3-5%  
   - 在本方案中的应用：审核团队3人Persona分工（4.2）；多视角独立诊断；**审核反馈回流**（3.5）——审核具体问题传给获胜Agent做反思改进

4. **MetaGPT: Meta Programming for Multi-Agent Collaborative Framework** (ICLR 2024)  
   - 核心发现：结构化文档替代自然语言聊天（Pass@1提升4.2-5.4%）；发布-订阅消息机制；角色消融实验  
   - 在本方案中的应用：聚焦输出Schema约束（3.5）；编排器FSM（6.1）；**完整6个SOP中间产物Schema**（6.2）——StudentProfile→CandidateOutput→ReviewFeedback→FocusedOutput→JudgeVerdict→ResourcePackage发布-订阅链
