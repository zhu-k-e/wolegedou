## 🔴 高严重度 — 详细解决方案

### 问题1：讨论不收敛

**风险描述**：3轮讨论后仍无共识，调用次数反超流水线，响应时间失控。

**解决方案：三层防线**

| 防线层 | 机制 | 触发条件 | 效果 |
|--------|------|---------|------|
| **第一层：早停** | 每轮结束后计算共识度，≥80%直接输出 | 任何轮次共识≥80% | 简单问题1轮即出，调用3~5次 |
| **第二层：硬上限** | MAX_DISCUSSION_ROUNDS=3，到3轮强制加权收敛 | 3轮仍未≥80% | 最坏情况3轮+1次收敛，调用可控 |
| **第三层：兜底** | 共识<60%时触发独立审核团介入（混合方案核心） | 3轮后共识<60% | 圆桌失败→审核团裁决，保证质量底线 |

**关键设计**：

```
Round 1: 提初稿 + 补充 → 计算共识度
  ≥80% → 直接输出（最快路径）
  <80% → 进入Round 2

Round 2: 质疑 + 修正 → 计算共识度
  ≥80% → 输出
  <80% → 进入Round 3

Round 3: 综合修订 → 计算共识度
  ≥60% → 加权收敛输出（正常兜底）
  <60% → 🔴 触发审核团介入（异常兜底）
```

**共识度计算公式**：

```python
consensus = Σ(importance_score_i × agreement_i) / Σ(importance_score_i)
# agreement_i = 1(完全同意), 0.5(部分同意/存疑), 0(反对)
# 领域专家权重更高 → 少数专家的反对不会被多数非专家淹没
```

**调用量对比**：

| 场景 | 最快路径 | 正常兜底 | 异常兜底(审核团介入) |
|------|---------|---------|------------------|
| 单领域无分歧 | 3~5次(1轮) | 6~8次(2轮) | 10~12次(3轮+审核) |
| 跨领域2段 | 6~10次(1轮) | 12~15次(2轮) | 18~22次(3轮+审核) |

> 异常兜底调用次数（18~22次）仍低于旧流水线固定25次，且**只在共识<60%的极端情况触发**。

### 问题2：Agent从众附和

**风险描述**：LLM天性顺从权威/多数意见，讨论变成"合谋"而非辩论，Debate论文的核心优势失效。

**解决方案：四重反从众机制**

| # | 机制 | 来源论文 | 具体实现 | 优先级 |
|---|------|---------|---------|--------|
| **①** | **反从众Prompt** | Debate(自信度隐藏) | 讨论Prompt强制包含："如有不同意见**必须**提出；如完全同意也需附**独立验证理由**，不得简单回复'同意'" | 必须 |
| **②** | **魔鬼代言人轮** | Debate(MaW→C转化) | 每轮讨论随机指定1位Agent为"质疑者"（Devil's Advocate），该Agent**必须**找到至少1个可质疑的点，即使它实际上同意 | 必须 |
| **③** | **隐藏置信度** | Debate(自信度隐藏防止锚定) | 讨论过程中Agent互不可见对方的self-assessed confidence，只看到对方的观点和论据 | 必须 |
| **④** | **结构化异议格式** | — | 不同意见必须用固定格式：`CHALLENGE: [具体质疑点] → EVIDENCE: [支持证据] → SUGGESTION: [修正建议]`。不允许只说"我有异议"不给证据 | 建议 |

**魔鬼代言人机制详解**：

```
Round 1: 所有参选Agent提初稿
  → 协调器随机选1位Agent标记为 DA
  → DA的Prompt额外追加："你必须找出至少1个可质疑的点"

Round 2: 非DA Agent补充 → DA质疑 → 其他Agent回应质疑
  → DA角色轮换（新的随机Agent成为DA）

Round 3: 综合修订（不再设DA，但Prompt仍要求不同意见）
```

**为什么有效**：
- Debate论文实验证明：强制少数方提出证据可触发MaW→C转化（少数方说服多数方）
- Devil's Advocate是**制度化**的质疑角色，不是靠Agent"自觉"质疑
- 即使DA内心同意，强制质疑仍能发现盲点（类似代码review中的"即使你觉得代码没问题也要再看一遍"）

### 问题3：锚定偏误

**风险描述**：参与者审核自己参与构建的结果，倾向认为自己贡献的部分没问题，难以客观评价。

**解决方案：三重脱锚机制**

| # | 机制 | 具体实现 | 效果 |
|---|------|---------|------|
| **①** | **贡献匿名化** | 收敛投票阶段，Agent看到的最终答案是**合并后**的完整版，不标注"这段是谁写的"。Agent只看内容质量，不看作者 | 消除"我写的=好的"偏误 |
| **②** | **跨域交叉验证** | Agent A（RAG专长）验证Agent B（LangChain专长）的LangChain相关结论；Agent B验证Agent A的RAG结论。**跨域验证打破自我锚定** | 用别人的视角审查自己的贡献 |
| **③** | **审核团盲审兜底** | 共识<60%时触发的审核团，成员**未参与讨论**，完全独立审核最终输出。审核团看到的是最终答案+讨论日志，但不知道谁主张了什么 | 纯第三方视角，零锚定 |

**贡献匿名化的具体实现**：

```python
# 讨论阶段：正常显示谁说了什么（需要知道是谁才能回应/质疑）
# 收敛投票阶段：合并所有贡献为一个完整答案文档
#   → 删除所有 "由Agent_X提出" 标注
#   → 仅保留内容本身 + 引用来源
# Agent投票时看到的是：
#   "以下是关于[主题]的综合结论：[匿名化内容]"
#   而非："Agent_A说X，Agent_B补充Y，Agent_C质疑Z"
```

**为什么跨域验证有效**：
- MAR论文发现：不同Persona的反思者能打破确认偏误
- 圆桌方案中Persona从领域专长自然涌现：RAG Agent天生关注检索策略准确性，LangChain Agent天生关注API调用正确性
- 跨域验证 = 让RAG Agent审查LangChain结论 → 它不会"锚定"在LangChain的视角上

## 🟡 中严重度 — 详细解决方案

### 问题4：职责分工不够"明确"

**风险描述**：赛题要求"至少3个明确职责分工的智能体"，圆桌讨论中Agent角色是动态的，不像旧方案有固定分工。

**解决方案：讨论内显式角色分配 + Agent Card标注**

**核心思路**：分工是**过程分工**而非**固定身份分工**。每个Agent在讨论中有明确的当下角色，角色按轮次轮换。

| 维度 | 旧方案（固定分工） | 新方案（过程分工） | 赛题对齐 |
|------|----------------|----------------|---------|
| 分工依据 | 固定身份（审核永远是审核） | 当下角色（提初稿者=主导，补充者=辅助） | ✅ 每次讨论都有3+个明确分工角色 |
| 分工数量 | 17个角色（冗余） | 每次讨论2~5个角色（精简） | ✅ 满足"至少3个" |
| 分工可追溯 | 固定不变 | discussion_rounds表记录每轮角色 | ✅ 可审查 |

**讨论角色定义**：

| 角色 | 职责 | 触发条件 | 轮次 |
|------|------|---------|------|
| **主导者(Leader)** | 提出初稿，定义讨论框架 | 置信度最高/标签最匹配的Agent | Round 1 |
| **补充者(Supplementer)** | 补充遗漏知识点、扩展覆盖面 | 标签次匹配的Agent | Round 1-2 |
| **质疑者(Devil's Advocate)** | 必须找出至少1个可质疑点 | 随机指定（轮换） | Round 2 |
| **验证者(Verifier)** | 检查事实准确性、引用有效性 | 跨域Agent自然承担 | Round 2-3 |
| **修订者(Reviser)** | 根据质疑整合修正后的版本 | 原主导者或被质疑者 | Round 3 |

**赛题对齐论证**：

> "我们的系统每次讨论至少产生3个明确分工角色（主导者、补充者、质疑者），分工基于Agent的领域专长和历史表现动态分配，而非固定身份。这比静态分工更灵活：同一Agent在不同问题中承担不同角色，体现了真正的多智能体协同。"

### 问题5：冷启动自参选阈值尴尬

**风险描述**：没有历史数据的Agent怎么自评估置信度？冷启动时importance_score=0.5（默认值），所有Agent都是"0.5"，无法区分谁更合适。

**解决方案：渐进阈值 + 标签匹配代理 + 强制轮换**

| 情况 | 机制 | 具体实现 |
|------|------|---------|
| **完全冷启动(count<3)** | 标签匹配代理 | 用tag_match_score替代importance_score作为置信度：`confidence = tag_match_score × 0.7 + 0.3`（基础分保底） |
| **部分冷启动(count 3~5)** | 渐进阈值 | 参选阈值从0.6降至0.4，允许更多Agent参与，通过实际讨论表现快速积累数据 |
| **成熟Agent(count≥5)** | 正常阈值 | 参选阈值恢复0.6，importance_score可信 |

**强制轮换机制**：

```python
# 每周至少1次强制征召
if agent.weekly_participation_count < 1:
    coordinator.force_recruit(agent, next_question_matching_tags)
```

> 保证每个Agent都有机会积累数据，不会永远卡在冷启动。

**冷启动期的讨论策略**：

- 冷启动Agent参与讨论时，角色优先分配为"补充者"（风险最低的角色）
- 主导者仍由成熟Agent承担
- 冷启动Agent的收敛投票权重降低（`weight = min(importance_score, 0.5)`）
- 经过3~5次参与后自动升级为正常权重

### 问题6：延迟不可预测

**风险描述**：旧方案固定9/19/37次调用，时间可预测。圆桌方案调用次数波动大（3~20次），响应时间不可预测。

**解决方案：分级响应模式 + 硬超时 + 流式UI**

| 模式 | 触发条件 | 最大轮次 | 最大时间 | 调用次数 | 适用场景 |
|------|---------|---------|---------|---------|---------|
| **快速模式(Fast)** | 学生选择/简单问题 | 1轮 | ≤10s | 3~5次 | 课后快速答疑 |
| **深度模式(Deep)** | 学生选择/复杂问题 | 3轮 | ≤30s | 8~15次 | 深度学习探讨 |
| **专家模式(Expert)** | 共识<60%自动触发 | 3轮+审核团 | ≤45s | 15~22次 | 极端分歧问题 |

**硬超时机制**：

```python
MAX_RESPONSE_TIME = 35  # 秒
if elapsed_time > MAX_RESPONSE_TIME:
    # 强制输出当前最佳共识版本
    output = best_convergence_so_far
```

**流式UI设计**：

```
[正在组队...] Agent A、B、C已参选
[讨论进行中 - 第1轮] A提初稿 → B补充中...
[讨论进行中 - 第2轮] C质疑 → A回应中...
[达成共识 ✓] 正在格式化输出...
```

> 学生看到实时进度，不会焦虑等待。类似ChatGPT的streaming效果。

### 问题7：跨段无桥梁Agent时断链

**风险描述**：多段问题时各段独立讨论，段间缺乏协调，可能产生矛盾结论。

**解决方案：协调器桥接 + 跨段引用 + 一致性快检**

| 机制 | 具体实现 | 调用次数 |
|------|---------|---------|
| **协调器桥接** | 协调器在讨论开始前，将前段的结论摘要注入当前段所有Agent的上下文 | 0次LLM（纯拼接） |
| **跨段引用协议** | 讨论Prompt增加："请注意前段已得出以下结论：[摘要]。如你的讨论与此矛盾，必须说明原因" | 0次额外调用 |
| **一致性快检** | 所有段讨论完成后，协调器用1次LLM调用检查段间一致性 | +1次LLM |

**跨段讨论流程**：

```
段1讨论完成 → 协调器提取段1结论摘要
  → 注入段2所有Agent的讨论上下文
  → 段2Agent在讨论时自然参考段1结论
  → 如有矛盾，段2Agent在讨论中提出
  → 所有段完成后 → 1次一致性快检 → 如发现矛盾 → 指定相关段再讨论1轮
```

**为什么不设专门的"桥梁Agent"**：
- 桥梁Agent会增加Agent数量（违背精简原则）
- 协调器本身就是桥接角色（它管理全局上下文）
- 跨段引用协议让每个Agent都承担桥接责任（分布式而非集中式）

### 问题8：调试困难

**风险描述**：讨论是动态过程，Agent的发言顺序、角色分配、质疑回应都是非确定性的，问题难以复现和定位。

**解决方案：结构化日志 + 回放 + A/B测试框架**

| 工具 | 具体实现 | 用途 |
|------|---------|------|
| **discussion_rounds全量记录** | 每轮记录：agent_id, contribution_type(propose/supplement/challenge/revise/agree), content_summary, references | 追溯每个Agent在讨论中的完整轨迹 |
| **回放脚本** | 从discussion_rounds重建完整讨论流程，按轮次+Agent逐条显示 | 复现问题场景 |
| **DEBUG_DISCUSSION模式** | 开发时设flag=1，每个Agent的完整推理过程（含内部思考）写入日志 | 定位Agent为何做出某个决策 |
| **A/B测试框架** | 同一问题同时跑流水线(v6.13)和圆桌(v7.0)，对比输出质量、时间、成本 | 验证圆桌方案的真实效果 |

**discussion_rounds表设计**：

```sql
CREATE TABLE discussion_rounds (
    id            INTEGER PRIMARY KEY,
    session_id    TEXT NOT NULL,           -- 关联学生会话
    question_id   TEXT NOT NULL,           -- 关联问题
    segment_idx   INTEGER,                -- 第几段(跨段问题)
    round_num     INTEGER NOT NULL,        -- 第几轮讨论
    agent_id      TEXT NOT NULL,           -- 哪个Agent
    role          TEXT NOT NULL,            -- leader/supplementer/DA/verifier/reviser
    contribution  TEXT NOT NULL,            -- propose/supplement/challenge/revise/agree
    content       TEXT,                    -- Agent发言摘要
    confidence    REAL,                    -- 自评估置信度(仅开发模式记录)
    references    JSON,                    -- 引用来源
    created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 问题9：实现复杂度

**风险描述**：讨论需要Agent间消息传递、角色轮换、共识计算，比流水线复杂度高。

**解决方案：讨论协议标准化 + 发布-订阅消息架构**

| 维度 | 标准化设计 | 说明 |
|------|----------|------|
| **讨论协议** | 6步接力构建（提初稿→补充→质疑→回应→修订→收敛） | 每步有固定输入/输出格式，Agent只需按协议操作 |
| **消息架构** | 发布-订阅模式（MetaGPT的发布-订阅消息） | 协调器广播每位Agent的贡献→所有参与者自动收到 |
| **Agent接口** | 统一接口：`receive(context) → respond(contribution)` | Agent不需要知道讨论的复杂逻辑，只负责收上下文、输出贡献 |
| **共识计算** | 纏程函数：`calculate_consensus(votes, weights) → float` | 独立模块，与讨论逻辑解耦 |

**为什么复杂度可控**：

- Agent总数从17→11，减少6个角色的实现
- 删除审核团6节+裁判团6节=12节详细设计 → 替换为讨论协议1节+收敛机制1节
- 讨论协议是**标准化的**，Agent实现只需遵循接口，不需要理解全局逻辑
- 协调器承担所有编排工作，Agent只做"收到上下文→输出贡献"

**实现路线**：

```
Phase 1: 实现协调器（讨论编排+共识计算+消息广播）
Phase 2: 10个领域Agent统一接口改造
Phase 3: 讨论协议Prompt设计+测试
Phase 4: 收敛投票+审核团兜底实现
```

### 问题10：token消耗未估算

**风险描述**：每轮讨论所有Agent看到历史消息，3轮×5Agent×历史累积 = token消耗可能很大。

**解决方案：压缩历史 + 渐进裁剪 + token预算**

| 机制 | 具体实现 | 节省效果 |
|------|---------|---------|
| **结构化摘要替代全文** | Round 2时，Agent不看到Round 1的完整发言，而是看到协调器生成的结构化摘要："已达成共识：[点1][点2]；仍存分歧：[点3]" | ~40% token节省 |
| **共识点裁剪** | 已达成共识(≥80%同意)的内容从后续轮次上下文中移除——既然已共识，无需再讨论 | ~20% token节省 |
| **token预算** | 每轮每位Agent max_tokens=500（讨论贡献），总预算上限=500×5×3=7500 tokens/次问答 | 硬上限防失控 |

### 问题11：收敛投票权重需论证

**风险描述**：收敛投票用importance_score作权重，但这个权重设计是否合理？领域专家权重更高是否会导致"专家独裁"？

**解决方案：继承三因子公式 + 可配置 + A/B验证**

**权重来源**（继承v6.13已论证的三因子公式）：

```
importance_score(tag, agent) = α × frequency_score + β × quality_score + γ × feedback_score
# α=0.4, β=0.35, γ=0.25（可配置）
# frequency_score: 该Agent在该标签上的历史参与频次
# quality_score: 该Agent在该标签上的历史输出质量
# feedback_score: 学生对该Agent的历史满意度
```

**这个公式在新架构中驱动3个环节**：

| 环节 | 权重作用 | 对应论文 |
|------|---------|---------|
| 自参选 | importance_score > 0.6 → 主动参选 | DyLAN |
| 讨论 | DA角色指定偏好低importance_score的Agent（新Agent更可能发现盲点） | Debate(MaW→C) |
| 收敛投票 | 每票权重=importance_score | Debate(per-tag权重) |

**防"专家独裁"设计**：

```python
# 权重上限：单Agent权重不超过总权重的40%
max_weight_ratio = 0.4
adjusted_weight = min(importance_score, total_weight * max_weight_ratio)
```

**A/B验证计划**：

| 实验组 | 权重方案 | 对比指标 |
|--------|---------|---------|
| A组 | importance_score加权(默认) | 输出质量、共识速度 |
| B组 | 平权投票(每票权重1) | 输出质量、共识速度 |
| C组 | 领域匹配度加权(tag_match) | 输出质量、共识速度 |

> 系统上线后运行A/B测试1个月，根据数据确定最优权重方案。

## 混合方案完整架构图

```
学生提问
  → 学情画像解析(LLM×1)
  → Agent自参选+协调器征召(0次LLM)
  → 圆桌讨论(≤3轮, LLM×3~15)
     │ 每轮：提初稿→补充→质疑(DA)→回应→修订
     │ 反从众Prompt + 隐藏置信度 + 结构化异议
  → 收敛投票(0次LLM, importance_score加权)
     │
     ├─ 共识≥80% ──────→ 直接输出 ✓
     │
     ├─ 共识60~80% ────→ 加权收敛输出 ✓
     │
     └─ 共识<60% ─────→ 🔴 触发审核团介入
                         │ 2名独立审核Agent(未参与讨论)
                         │ 盲审最终答案+讨论日志
                         │ 审核团裁决(LLM×2~4)
                         ↓
                       审核团输出 ✓
  → 格式化 + 资源生成(LLM×1~3)
  → 输出 + 贡献记忆更新
```

**正常路径（90%+场景）**：圆桌讨论→收敛→输出（3~15次LLM）
**异常路径（<10%场景）**：圆桌讨论→审核团兜底→输出（15~22次LLM）
