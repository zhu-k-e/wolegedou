# 流水线架构最优改进方案：赛题要求 × 四篇论文

> **前提**：不改变流水线整体结构（学情诊断→候选生成→审核→聚焦→裁判→资源生成），仅在每个阶段内部做机制升级，让四篇论文真正落地而非"贴标签"。

---

## 一、赛题核心诉求重新解读

赛题表面提了7条要求，但内核只有三个字：**协同决策**。

| 赛题原文 | 评委真正想看到的 | 当前流水线的问题 |
|---------|----------------|----------------|
| "至少3个明确职责分工的智能体" | Agent之间有**交互**，不是各自独立工作后拼接 | 17个角色各干各的，候选Agent互不可见，审核只看结果不看过程 |
| "分析-生成-校验-决策协同闭环" | 闭环中有**反馈回流**，不是单向流水线 | 流水线是单向的：生成→审核→裁判，审核反馈不回流传给生成Agent |
| "引入辩论与交叉验证机制" | Agent之间**互相质疑**，不是第三方评分 | "辩论"发生在裁判之间，内容生产者（候选Agent）之间没有辩论 |
| "消除大模型幻觉" | 机制本身能**主动发现并纠正**幻觉，不是靠概率碰运气 | 反向怀疑是被动触发的（看输出特征），不是主动质疑 |
| "高保真知识溯源" | 每条结论都能追到**具体来源**，且有验证过程 | 有溯源标注，但溯源是裁判事后补的，不是生成时强制的 |

**一句话诊断**：当前流水线满足了赛题的"形"（有审核、有裁判、有博弈），但缺了赛题的"魂"（Agent之间的真正交互与反馈回流）。

## 二、四篇论文核心洞察重新提取

### 2.1 每篇论文的"一句话真谛"

| 论文 | 方案书当前写的 | 论文真正的核心洞察 | 差距 |
|------|--------------|-------------------|------|
| **DyLAN** | "Agent Importance Score动态打分+动态淘汰" | Agent应该**根据当前问题自评估相关性**，不相关的Agent主动退出，而非仅靠历史分数被动遴选 | 有"历史分"无"当下分"——Agent不会对具体问题说"这个问题我不擅长" |
| **Debate** | "废除多数投票，改为证据裁决+异议保护" | 辩论的价值在于**MaW→C转化**（多数错误时少数纠正多数），关键条件是少数方必须看到多数方的论证后才能有效反驳 | 当前"辩论"在裁判之间，候选Agent（内容生产者）之间没有辩论——真正懂内容的人没参与辩论 |
| **MAR** | "审核团队3人Persona分工+多视角独立诊断" | 核心是**反思**——Agent在收到反馈后改进自己的输出，不是第三方打分就完事 | 当前审核只评分选最优，**反馈没有回流给生成Agent**——赢的Agent不知道自己哪里可以更好 |
| **MetaGPT** | "聚焦输出Schema约束+SOP中间产物+FSM" | 核心是**完整SOP链**：每个角色产出结构化文档，下游角色基于文档工作，而非基于自然语言聊天 | 当前只定义了FocusedOutput一个Schema，其他中间产物（候选输出、审核反馈、裁判裁决）没有标准化Schema |

### 2.2 当前方案书的"贴标签"问题

```
当前论文映射（proposal.md 1.4节）：

DyLAN  → importance_score + 动态淘汰     ← 只用了"打分"和"淘汰"，没用"动态自评估"
Debate → 证据裁决 + 异议保护             ← 只用了"裁决机制"，没用"内容生产者辩论"
MAR    → 3人Persona分工                 ← 只用了"多视角评分"，没用"反思改进"
MetaGPT → FocusedOutput Schema + FSM    ← 只用了"结构化输出"，没用"完整SOP链"

本质：每篇论文只取了"工具层"（怎么打分/怎么裁决/怎么分工/怎么约束），
      丢了"机制层"（为什么动态/为什么辩论/为什么反思/为什么结构化）。
```

## 三、流水线内的5个最优改进点

> 以下5个改进**不改变流水线结构**，只在阶段内部升级机制。每个改进对应一篇论文的真正落地。

### 改进1：候选自评估（DyLAN真正落地）

**位置**：模块二 3.4 候选输出机制

**当前流程**：
```
调度员选2个候选 → 两个Agent并行输出 → 审核团队评分选最优
```

**改进后**：
```
调度员选2个候选 → 两个Agent并行输出 + 自评估置信度 → 审核团队评分选最优
                     ↑ 新增
```

**具体设计**：
```
每个候选Agent在输出答案的同时，额外输出一个 self_confidence 字段：

{
  "answer": { ...FocusedOutput... },
  "self_confidence": {
    "score": 0.85,          // 0-1，对自己回答这个问题的信心
    "weak_points": ["对LangChain v0.3的新API不确定", "代码示例未验证过"]
  }
}

自评估规则：
  - Agent被要求诚实评估：如果问题涉及你的secondary_functions，confidence应≤0.7
  - 如果两个候选的self_confidence都<0.5 → 触发知识库RAG增强（给两个Agent都补充检索结果后重新生成）
  - self_confidence不计入审核评分，但作为裁判团的参考输入
```

**为什么这是DyLAN的真正落地**：
- DyLAN的核心是Agent**根据当前任务动态评估自己的相关性**，不是只靠历史分数
- 当前方案的importance_score是"过去表现"，self_confidence是"当下判断"
- 两者结合 = 历史分（调度员用）+ 当下分（系统用）= DyLAN的完整动态选择

**额外调用**：0次（自评估在同一轮LLM调用中输出，不额外增加调用）

### 改进2：审核反馈回流（MAR真正落地）

**位置**：模块三 4.2 审核团队 → 模块二 3.5 聚焦输出

**当前流程**：
```
审核团队3人评分 → 选出最优Agent → 最优Agent"确认并完善输出"（不知道审核反馈）
```

**改进后**：
```
审核团队3人评分 → 选出最优Agent → 最优Agent看到审核反馈后改进输出（反思）
                                     ↑ 新增：反馈回流
```

**具体设计**：
```
当前聚焦输出Prompt（3.5节）：
  "你在段内评选中获胜。请确认并完善你的输出。"

改进后聚焦输出Prompt：
  "你在段内评选中获胜。以下是审核团队对你输出的具体反馈：
   
   Verifier反馈：{fact_accuracy发现的具体问题，如"第2条知识点缺少知识库依据"}
   Skeptic反馈：{logic_completeness发现的具体问题，如"步骤3到步骤4缺少过渡逻辑"}
   Evaluator反馈：{pedagogical_fit发现的具体问题，如"对入门学生使用了未解释的术语"}
   
   请针对以上反馈改进你的输出，并标注哪些地方做了修改。"

注意：
  - 审核团队只传"具体问题"给Agent，不传"评分数字"（防止Agent只追求分数）
  - 如果审核团队没有发现问题（3人全高分），聚焦输出走原始流程（确认+完善）
  - 这不是"退回修改"，是"赢者精进"——Agent知道赢了，但还知道哪里可以更好
```

**为什么这是MAR的真正落地**：
- MAR的核心发现：单Agent输出存在确认偏误，**反思后改进**能显著提升质量
- 当前方案的审核反馈只用于"选谁赢"，浪费了反馈的诊断价值
- 反馈回流后，聚焦输出不再是"格式化补全"，而是"有针对性的改进"
- MAR论文实验：反思后Pass@1提升3-5%

**额外调用**：0次（反馈整合进聚焦输出的同一轮调用中）

### 改进3：候选辩论（Debate真正落地）

**位置**：模块三 4.4 裁判团 4.4.2 错误博弈状态机

**当前流程**：
```
裁判团3人独立审查 → 2:1分歧 → DEBATING（少数方举证） / PROTECTING（异议保护）
                              ↑ 2:1和1:2是同一局面，PROTECTING是死路径
```

**改进后**：
```
裁判团3人独立审查 → 3:0全票通过 → PASSED
                  → 2:1分歧 → 分歧解决机制（合并DEBATING和PROTECTING）
                               ↓
                    少数方提交书面证据 → 多数方回应 → 裁判长裁决
                               ↓
                    另外新增：候选Agent之间的辩论（内容生产者层面的交叉验证）
```

**具体设计——分两层辩论**：

**第一层：裁判团分歧解决（修复死路径）**：
```
合并DEBATING和PROTECTING为统一的"分歧解决"路径：

[COMPARING] 汇总三人判断
  ├─ 3:0 → [PASSED]
  └─ 2:1 → [DISSENT_RESOLVE] 分歧解决
              ↓
              少数方（1人）提交书面证据：
                - 证据类型1：知识库检索结果
                - 证据类型2：检查清单条目
                - 证据类型3：学情画像字段
              ↓
              多数方（2人）必须回应：
                - 接受证据 → 改判 → [REVISING]
                - 反驳证据 → 维持原判 → [PASSED]
              ↓
              若双方僵持（少数方坚持+多数方不接受）：
                → 裁判1（事实审查）做最终裁决（因为事实准确性优先级最高）
              
              修改上限：2次（超过则强制通过，标注"低置信度"）
```

**第二层：候选Agent辩论（新增，Debate论文核心）**：
```
触发条件：裁判团触发[DISSENT_RESOLVE]时，同时触发候选辩论

流程：
  1. 裁判团分歧中的"少数方观点"被 anonymized 传给落选候选Agent
     （不告诉它"你输了"，只告诉它"有人对这个问题提出了以下质疑"）
  
  2. 落选候选Agent可以：
     - 认同质疑 → 提交补充证据支持少数方观点
     - 不认同质疑 → 提交反驳证据
  
  3. 获胜候选Agent（已产出聚焦输出）也收到同样的质疑：
     - 必须针对质疑提交辩护证据
  
  4. 两方证据合并提交给裁判团，作为分歧解决的额外输入

效果：
  - 真正懂内容的Agent参与辩论（不是只靠裁判判断）
  - 落选候选的"专业知识"不被浪费——它可能看到获胜者没看到的问题
  - 这是Debate论文的MaW→C转化路径：少数方（可能是正确的）有机会用证据说服多数方
```

**为什么这是Debate的真正落地**：
- Debate论文的核心场景就是**内容生产者之间的辩论**，不是第三方评审
- 当前方案只在裁判之间辩论，裁判是"外行审查内行"——真正懂领域的是候选Agent
- 候选辩论让内容生产者直接参与交叉验证，这才是赛题要的"辩论与交叉验证"
- 合并DEBATING/PROTECTING同时修复了17项问题中的#4死路径bug

**额外调用**：1-2次（仅在裁判团出现2:1分歧时触发，约30%场景，平均增加0.3-0.6次调用）

### 改进4：完整SOP中间产物链（MetaGPT真正落地）

**位置**：全文——新增一节"SOP中间产物定义"

**当前状态**：只定义了FocusedOutput一个Schema，其他中间产物散落各处无统一规范

**改进后**：定义完整的6个结构化中间产物

```
SOP中间产物链（每个产物有明确Schema，下游只能基于上游产物工作）：

Stage 1 → StudentProfile JSON     （学情画像，模块一输出）
Stage 2 → CandidateOutput JSON    （候选输出+自评估，模块二输出）
Stage 3 → ReviewFeedback JSON     （审核反馈，模块三输出）← 新增Schema
Stage 4 → FocusedOutput JSON      （聚焦输出，模块二输出，已定义）
Stage 5 → JudgeVerdict JSON       （裁判裁决，模块三输出）← 新增Schema
Stage 6 → ResourcePackage JSON    （资源包，模块二输出）

继承关系：
  StudentProfile → 被 Stage 2/3/4/5/6 订阅（所有下游都需要学情信息）
  CandidateOutput → 被 Stage 3 订阅（审核团队基于候选输出评分）
  ReviewFeedback → 被 Stage 4 订阅（聚焦输出基于审核反馈改进）← 改进2的载体
  FocusedOutput → 被 Stage 5 订阅（裁判团基于聚焦输出审查）
  JudgeVerdict → 被 Stage 6 订阅（资源生成基于裁决结果生成）
```

**新增的两个关键Schema**：

```json
// ReviewFeedback JSON Schema（审核反馈，目前没有标准化定义）
{
  "seg_id": "seg_1",
  "candidates": [
    {
      "agent_id": "Agent_4",
      "scores": {
        "fact_accuracy": 0.92,
        "logic_completeness": 0.80,
        "pedagogical_fit": 0.85
      },
      "issues_found": [
        {
          "reviewer": "Verifier",
          "severity": "medium",
          "location": "knowledge_refs[1]",
          "description": "第2条知识点缺少知识库依据，标注为'待验证'"
        },
        {
          "reviewer": "Skeptic",
          "severity": "low",
          "location": "reasoning_steps[2]",
          "description": "步骤3到步骤4缺少过渡逻辑"
        }
      ],
      "is_winner": true
    }
  ],
  "cross_segment_issues": []  // 跨段问题（仅多段场景）
}
```

```json
// JudgeVerdict JSON Schema（裁判裁决，目前没有标准化定义）
{
  "verdict": "passed | revise | low_confidence_passed | failed",
  "judges": [
    {
      "role": "事实审查",
      "judgment": "pass | fail",
      "evidence": ["知识库检索结果1", "知识库检索结果2"],
      "confidence": 0.92  // 对外隐藏，仅系统内部记录
    },
    // ... 裁判2、裁判3
  ],
  "dissent_resolution": null | {
    "minority_judge": "裁判2",
    "evidence_submitted": [...],
    "majority_response": "accepted | rejected",
    "candidate_debate": null | {
      "challenging_agent": "Agent_7",
      "challenge_evidence": [...],
      "defending_agent": "Agent_4",
      "defense_evidence": [...]
    }
  },
  "traceability": [
    {
      "statement": "ConversationBufferMemory适用于保留完整对话历史",
      "source": "LangChain官方文档 v0.2 - Memory章节",
      "verification_status": "已验证"
    }
  ],
  "overall_verification_rate": 0.94
}
```

**为什么这是MetaGPT的真正落地**：
- MetaGPT的核心是**完整SOP链**——不是一两个Schema，而是从输入到输出的全链路结构化
- 当前方案的审核反馈和裁判裁决都是"自然语言+零散JSON"，下游无法标准化消费
- 定义完整SOP链后，每个阶段的输入输出都是确定性的，调试和迭代都有据可查
- 发布-订阅模式：Stage 4订阅ReviewFeedback的`issues_found`字段做反思改进（改进2的载体）

**额外调用**：0次（纯Schema定义，不增加LLM调用）

### 改进5：分层模型策略（成本控制，解决problem_report #8）

**位置**：新增"成本控制机制"一节

**当前问题**：所有阶段都用同一个LLM（如GPT-4o），9次调用×$0.05-0.15/次 = $0.45-1.35/次问答

**改进设计**：
```
分层模型策略——不同阶段用不同模型等级：

| 阶段 | 模型等级 | 推荐模型 | 单次成本 | 理由 |
|------|---------|---------|---------|------|
| 学情画像生成 | 中档 | DeepSeek-V3 | ~$0.01 | 结构化分类任务，不需要顶级推理 |
| 候选Agent输出 | 中档 | DeepSeek-V3 | ~$0.01 | 需要领域知识但不需要顶级推理 |
| 候选自评估 | 低档 | GPT-4o-mini | ~$0.002 | 只需判断置信度，不需要生成内容 |
| 审核团队评分 | 中档 | DeepSeek-V3 | ~$0.01 | 需要理解内容但评分维度固定 |
| 聚焦输出（含反思） | 高档 | GPT-4o | ~$0.05 | 最终质量决定环节，需要顶级推理 |
| 裁判团裁决 | 高档 | GPT-4o | ~$0.05 | 事实核查和逻辑审查需要顶级能力 |
| 资源生成 | 中档 | DeepSeek-V3 | ~$0.01 | 格式化转换，不需要顶级推理 |

单领域成本估算（改进后）：
  画像1×$0.01 + 候选2×$0.01 + 自评估0 + 审核3×$0.01 + 聚焦1×$0.05 + 裁判3×$0.05 + 资源1×$0.01
  = $0.01 + $0.02 + $0.03 + $0.05 + $0.15 + $0.01
  = $0.27/次问答

对比当前（全GPT-4o）：
  9×$0.05-0.15 = $0.45-1.35/次问答
  
降本幅度：40-80%
```

**为什么这不是脱离论文的额外改进**：
- DyLAN论文的另一个发现：不是所有Agent都需要最强模型，弱模型在特定任务上足够
- 分层策略让"高质量模型用在最关键环节"成为设计原则，而非"全用最好的"

## 五、改进后的赛题对齐

| 赛题要求 | 改进前对齐 | 改进后对齐 | 提升点 |
|---------|-----------|-----------|--------|
| "辩论与交叉验证" | 裁判团错误博弈（2:1触发，有死路径） | 候选Agent辩论 + 裁判团分歧解决 | 真正的"辩论"在内容生产者之间发生 |
| "协同闭环" | 单向流水线 | 审核反馈回流到生成Agent | 闭环中有反馈回流 |
| "消除幻觉" | 反向怀疑（被动触发） | 候选辩论（主动质疑）+ 反馈回流改进 | 主动发现+纠正 |
| "高保真溯源" | 裁判事后补标注 | SOP链中每步都有结构化溯源字段 | 溯源是生成时强制，不是事后补 |
| "明确职责分工" | 17个角色各干各的 | 每个角色有明确的"发布什么+订阅什么" | 职责通过SOP接口定义 |
