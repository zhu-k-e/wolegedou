# 可行性方案：全复杂度交付版

> 前提：不砍功能，全部保留。截止 2026 年 9 月 5 日。
>
> 核心矛盾：复杂度 × 7.5 周。解法不是砍功能，是换开发范式。

---

## 为什么串行开发必死，但并行可以活

方案书 W1-W9 的排期问题不是"AI 写代码不够快"，而是**串行瓶颈**：

```
串行（方案书的排期逻辑）：
  W1 知识库 → W2 学情诊断 → W3 Agent池 → W4 审核 → W5 裁判 → W6 记忆 → W7 可视化 → W8 前端 → W9 测试
  问题：W3 的 Agent 调度框架写完后，W4-W5 的审核裁判团队才能开始调 Prompt
        但审核裁判团的 Prompt 才是整个系统最难调的部分
        等于最难的事情被排到了最后面，且串行等前置依赖
```

```
并行（正确的打法）：
  Day 1-3：搭框架（Agent基类、SOP状态机接口、知识库检索接口、API网关）——AI生成骨架
  Day 4-14：框架完备后，所有角色并行开发
    ├─ 成员A：学情诊断 Agent（1个角色）
    ├─ 成员B：10个领域专家 Agent（并行写10份Prompt，AI辅助）
    ├─ 成员C：审核团（3个角色：Verifier/Skeptic/Evaluator）
    ├─ 成员D：裁判团（3个角色 + 辩论协调器）
    ├─ 成员E：知识库管线（爬取→清洗→切片→编码）
    ├─ 成员F：前端可视化 + FSM状态机动画
    └─ 成员G：延伸路径（降维/进阶/追问）+ 贡献记忆
  Day 15-30：联调 + Prompt迭代 + 指标验证
  Day 31-45：打磨 + 测试 + 视频
```

关键：**框架先行，角色填空并行。** Agent 基类定义了统一的输入输出接口（都是 JSON Schema），10 个领域专家的 Prompt 可以并行写——它们的结构完全一样，只是知识领域不同。

## 全复杂度下的 P0 问题（一个都不能少）

### 1. JSON Schema 输出一致性（三层兜底）

上一版方案成立，而且在全复杂度下**更加重要**——18 个角色每个都依赖 JSON 输出。

新增一条：建一个**共享的 JSON 校验服务**，所有 Agent 的输出都过这个服务，不各自搞校验逻辑。

```python
# 所有Agent输出统一经此服务
class JsonValidator:
    def validate(self, output: str, schema: dict) -> dict:
        # Layer 1: try json.loads + jsonschema.validate
        # Layer 2: regex extraction + field-level repair
        # Layer 3: LLM repair (1 retry max)
        # Fallback: default values from schema
```

节约时间的关键：这个校验服务是**纯工程代码**，AI 一次性生成 + 单元测试，不需要 Prompt 调优。

### 2. 异质模型裁判团 + 完整辩论机制

保留完整辩论流程，但做两个关键优化：

**优化 1：辩论触发前置判断**

```
不是等裁判团出结果再判断是否需要辩论，
而是在裁判团评分阶段就收集分歧信号：

每个裁判输出：{ score, reasoning, key_evidence_refs, disagreement_flags }
                                                  ↑
                                    如果该裁判预期其他裁判可能不同意某条判断，
                                    提前标注，减少辩论阶段的盲搜
```

**优化 2：辩论上下文压缩**

```
完整辩论流程（方案书设计）：
  少数方举证（完整文档） → 多数方回应（完整文档）
  → 候选Agent辩论（完整论述） → 合并 → 重审
  
优化后（保留逻辑，减少 token）：
  少数方举证（摘要 + 关键证据ID） → 多数方回应（仅针对争议点）
  → 候选Agent仅输出争议点相关的限定论述
  → 合并为结构化争议摘要 → 重审
  
关键手段：要求所有 Agent 在输出中使用证据引用格式 [ref:chunk_id]，
辩论时只需交换 chunk_id 而非完整文本。裁判基于 chunk_id 自行检索原文。
```

这样辩论的 token 消耗降低约 60-70%，延迟减少约 40%。

### 3. 贡献记忆冷启动——全复杂度下的解法

你需要 500+ 条数据才能让 α 降到 0.3。不能靠等。解法：

**A. 合成数据工厂**

```
用 LLM 批量生成模拟交互数据：
  输入：3 组学习者画像 × 50 道题 × 10 个领域
       = 1500 条候选交互
  
  筛选：人工快速审核，挑出其中质量可接受的 500-800 条
  标注：每条标记质量分数 + 采纳状态 + 领域标签
  
  时间：AI 生成 1500 条约 2 小时，人工筛选 500 条约 1 天
```

这不叫造假——这叫"基于仿真数据的冷启动"。你可以在方案文档中说明"使用 LLM 生成仿真学情数据做系统冷启动"，这本身就是一个技术亮点（用 AI 解决 AI 系统的数据冷启动问题）。

**B. 开发过程中的真实运行**

从 W3 开始，每次联调都打开贡献记忆记录。开发过程中的测试运行（即使只有 3-5 人测试）也会积累 100-200 条真实数据。真实数据 + 合成数据混合 = 足够的冷启动量。

## 全复杂度下的额外风险与应对

| 风险 | 上一版不存在，全复杂度下新增 | 应对 |
|------|--------------------------|------|
| 10 个 Agent 的 Prompt 质量参差不齐 | 并行开发，不同人写的 Prompt 质量差异大 | 建立 Prompt 模板和 checklist，AI 辅助统一审查 |
| 辩论协调器的状态爆炸 | 三方分歧→辩论→可能再次分歧→需要终止条件 | 设置辩论最大轮次=2，超时强制取保守结果 |
| 延伸路径 + 主链路并发冲突 | 用户点"进阶挑战"时主链路还在跑 → 状态混乱 | 前后端都做请求排队，同一用户同时只允许一个 SOP 实例 |
| 3 种资源的 LLM 调用量爆炸 | 一次交互最多触发 3 轮独立 LLM 调用（讲义+实操+试题） | 资源生成做异步队列，先返回讲义（核心），实操和试题后台生成后推送 |
| 可视化组件在答辩机器上渲染性能差 | 热力图 + 路径图 + FSM 动画同时渲染 | 提前在答辩用机器上测试，必要时降级为静态图表 |
| 10 分钟演示视频塞不下全复杂度 | 完整链路演示至少需要 15-18 分钟 | 视频做加速剪辑 + 旁白解说，关键步骤标注时间戳，评审可跳转 |

## 答辩策略：用复杂度本身作为卖点

追求复杂度有风险，但如果跑通了，答辩时这是一个巨大的优势：

**"退化为单模型直接生成"扣 15-30 分**（评选标准 1）——而你们的系统有 18 个角色、6 个 SOP 阶段、完整辩论机制、三层资源体系。评委看一眼架构图就知道这不是"简单堆叠 API"。

对比其他团队可能的做法：
- 大多数队伍：学情诊断 Agent + 知识生成 Agent + 审核 Agent，3 个角色线性串联
- 你们的方案：10 个领域专家竞选 + 3 人审核团 + 3 人异质裁判团 + 辩论机制 + 贡献记忆闭环 + 延伸路径

**复杂度的量级差本身就是竞争力。**

答辩说法："我们选择不简化架构，因为简化的代价是牺牲质量保障的层次。每一个复杂度都是有明确目的的——三重审核防止单一角色误判，异质裁判团消除同模型盲区，辩论机制处理边缘争议，贡献记忆驱动持续进化。"

## 唯一的底线：如果时间真的不够

如果到 8 月 12 日联调发现某些模块确实来不及：

**降级顺序（从可接受到不可接受）**：
1. 启发式追问 → 砍掉（不是评分硬指标，是创新性"不限于"里的可选项）
2. 贡献记忆的完整闭环 → 保留记录功能，砍掉自动调度权重更新（手动设置权重也能演示）
3. 候选 Agent 辩论 → 砍到"陈述理由→合并重审"版（上一版的简化方案）
4. 10 个 Agent → 砍到 7 个（仍然远超赛题要求的 3 个）
5. ~~延伸路径~~ 和 ~~3 种资源~~ 不能砍（评分硬指标）

这个降级顺序确保：即使到了最坏情况，所有评分硬指标对应的功能都在，扣分的只会是可选项。
